# CLAUDE.md — TIA-Portal-Add-Ins

Working instructions and the decision record: what was chosen, what was rejected, and why. The technical documentation — Siemens DLL paths, Publisher mechanics, API surface, gotchas — lives under `docs/`, imported at the bottom. **Do not duplicate any of it here**; this file holds reasons, `docs/` holds facts.

**"The VM" throughout means the test machine with TIA Portal V20 and V21 installed.** The development PC has neither, and does not need them: everything up to the `.addin` package builds without TIA, which is why "verified here" and "confirmed on the VM" are different claims and are kept apart.

## Language

- **All documentation, code, comments and commit messages: English.** That is the rule for anything committed, and it holds for any contributor.
- The maintainer works in Spanish, so a conversation may be in Spanish while everything it produces is in English.

## Rules not to break

- **V20 — never add `Siemens.Engineering.dll`** to a project that already references `Siemens.Engineering.AddIn.dll`. The latter already carries the full object model (2269 types, including `HW.*` and `SW.Blocks.*`). Referencing both makes `IEngineeringObject` ambiguous and forces `extern alias`. Only reconsider if a specific type actually fails to compile.
- **V21 — the model is inverted**: `Siemens.Engineering.AddIn.Base.dll` holds only 71 infrastructure types, so `Siemens.Engineering.Base.dll` **must** also be referenced for `TiaPortal`, `Project`, `IEngineeringObject` and `NotificationIcon`. Nothing is duplicated there, so no `extern alias` is ever needed. `PlcBlock` lives in `Siemens.Engineering.Step7.dll`; there is no `Siemens.Engineering.Hmi.dll`.
- **The V21 Publisher is in `V21\`, not `V21\net48\`** — it cannot be derived from the assembly path the way it can in V20.
- **`PlatformTarget` = `x64`** in every project TIA loads into its process.
- **`<Private>False</Private>`** on every reference to a Siemens assembly.
- **Siemens DLL paths parameterized** through `$(SiemensPublicApi)`, never hardcoded in each `HintPath`.
- **TIA runs an Add-In in partial trust.** Confirmed on the VM by a `System.Security.SecurityException` out of `DataContractJsonSerializer.WriteObject`: *"the data contract type ... is not serializable in partial trust because it is not public"*. Any type a serializer touches must be **visible** — public, and public all the way out if nested. The sandbox is real and it is tight; when something works here and fails there, suspect trust before suspecting logic. A restricted `AppDomain` (`PermissionSet` with only `SecurityPermissionFlag.Execution`) reproduces it without TIA.
- Classes TIA instantiates by reflection (`AddInProvider`, `AddInController`) must be **`public`**. If they are `internal` the build succeeds and the Add-In never appears — a silent failure. Adapters are `internal sealed`.
- **Where a type goes is decided by its dependencies**, per the three-layer rule below. Both `Core` and `AddIn.Shared` stay **AnyCPU**; only the version projects are `x64`.
- **Adapters convert Siemens types into primitives or DTOs before crossing a layer.** `Project` stays in the version project; the action receives `project?.Name`.
- **Never name a namespace `AddIn.Core`.** Inside `namespace AddIn`, the identifier `Core` would then resolve to `AddIn.Core` before the global `Core`, breaking every qualified reference with a misleading "type does not exist" error.
- **The same trap from the other side: no `Core` type named like a satellite.** Inside `namespace Satellite.CodingStyleReport`, a type called `CodingStyleReport` resolves to the namespace — "is a namespace but is used like a type" — which is why the report document is `Core.Checks.StyleReport` (2026-09-13).
- **An Add-In may not keep a Siemens engineering object in a field, a property or a static**, and the Publisher enforces it: it inspected the assembly and refused to package it, with *"Engineering object '_process' of type 'Siemens.Engineering.AddIn.Utilities.Process' ... should not be defined as a field, property or as a static member. TIA Portal V20 onwards Add-Ins do not reload after each execution and member variables are not reinitialized automatically"* (2026-09-15, found while giving the report window a handle to write into later). The build fails at the Publisher step, not at the compiler, so the error names a type rather than a line. **The fix is to pass the work inwards rather than hand the object out**: `IProcessLauncher.Start(fileName, arguments, Func<string> payload)` keeps the process a local variable of the adapter while the caller works for minutes inside the delegate.
- Any assembly beyond the Add-In's own must be declared in `Config.xml` under **`AdditionalAssemblies`**, or TIA throws `FileNotFoundException` at runtime even though everything built and packaged cleanly.
- Assets live once in `assets/`, grouped **by feature**, and are embedded **in `AddIn.Shared`** as `EmbeddedResource` (never `Content`: the `.addin` only carries assemblies). Use a glob, not a list.
- **The loader and the assets cannot be separated.** Embedded resources are scoped to the assembly that carries them, and `Assets` resolves against `typeof(Assets).Assembly`. Moving `Assets.cs` without moving the `EmbeddedResource` glob makes every lookup return `null` — **silently**, because `Open` returns `null` by design so callers degrade.
- **Never hardcode a resource-name prefix.** Match on the tail of the name — a stale prefix compiles fine and returns `null` at runtime inside TIA.
- **A button that removes something uses the `Destructive` style, and every one of them does.** Identical to `Quiet` at rest and **red under the pointer**, so the click announces itself before it happens — and announces itself the same way wherever a remove button appears. Its template is spelled out rather than derived from `Quiet` with `BasedOn`, because the state that differs is a trigger *inside* the template and `BasedOn` cannot reach into one.
- **Every satellite with a form uses `UI.Shared/Controls/BrandHeader.xaml`, and none writes its own header.** Extracted 2026-09-16 when the maintainer asked for one size and format everywhere and the four windows turned out to carry three: a 38-pixel logo with an 18-point SemiBold title in two of them, 34 and 17 in a third, 28 with a plain-weight title in the fourth — and two of them painting the line under the title with the hex literal `#7E8899` instead of `InkMuted`, which is the same trap `Theme.xaml` exists to close. `Title`, `Subtitle` and `Badge` are dependency properties; the last two collapse while empty, so a window that sets only a title leaves no gap. **`Satellite.About` is deliberately not a consumer** — it has no form, the logo *is* its content at 300 pixels, and applying the rule there would be applying it against its own purpose. Measured by hosting the control and reading back what it painted, because "the same everywhere" is a claim about pixels rather than about markup.
- **Every satellite with a form also carries `UI.Shared/Controls/StatusBar.xaml`, and none writes its own status line.** Extracted 2026-09-18 when the maintainer asked for one look across every UI, and the four of them turned out to carry three margins and two inks for the same line: 12 pixels above it in one, 14 in another, 16 in a third, and that third painting it `InkMuted` where the rest used `Ink`. It is the same drift `BrandHeader` was pulled out of two days earlier, at the other end of the same windows. `Text` is a dependency property, so `StatusLine.Text = "…"` compiles unchanged. **The bar is there whether there is a status or not** — that is what the maintainer asked for in those words, and `MinHeight` is what reserves it: a bar that appears with its first message moves everything above it, and a window that resizes itself as it works reads as one that cannot make up its mind. **Trimmed with the whole of it on hover, never wrapped**, for the same reason. **`Satellite.About` is a consumer here where it is not of `BrandHeader`**, and the asymmetry is deliberate: it has no form, so a header would be the rule against its own purpose, but a bar is the rule's own case — a window that never has anything to say is exactly "even when there is no status".
- **A button's size lives in `Controls.xaml`, not in the windows.** Each window had been setting its own `Padding="0,N"` and the four had drifted through **seven** values — 1, 2, 3, 4, 5, 6, 7 and 8 — for one kind of control, which is how a row of buttons ends up looking assembled rather than designed. `Quiet` (and so `Primary`) and `Destructive` now carry `MinHeight="28"` and `Padding="10,0"`, and the windows carry none. **`MinHeight` rather than padding is what makes them one height**: padding decides a button's height only until something else does, so a fixed `Width` with a long label and a fixed `Width` with a glyph came out differently however carefully the padding was matched. **The horizontal padding is small on purpose** — most buttons here carry an explicit `Width` and padding eats into it, a `✕` in a 32-pixel button having nothing to spare; auto-width buttons get their room from it, which is why it is not zero. **A button that stretches to its row is right, not drift**: a `...` matching the height of the folder box beside it is the point. What must never differ is two buttons in the same row, which is what the check asserts.
- **A list, a tree or a table sits on `Surface`, inside a `Border` that paints it** — the coding-style report's rows, the snapshot's block list and the core updater's two trees, with the control itself `Transparent` on top. A container with no background of its own shows the window's gradient through, which is the one thing in the framework that reads as a panel and a container at once. **`Satellite.ConfigEditor` uses `Field` and is deliberately left alone**: it paints all four of its containers that way — the rule list, the interface area, the type rows and the hierarchy tree — so there it is a system rather than a drift, and changing one of them would be the only inconsistency in that window.
- **The dark-theme control styles live in `UI.Shared/Resources/Controls.xaml`, and a windowed app merges that one dictionary** — it pulls `Theme.xaml` in itself. Do not copy styles into a window: they moved out of `Satellite.DataBlockSnapshot` on 2026-09-09 precisely because a second consumer appeared. Most are **implicit**, so a plain `<TextBox/>` is themed already; only real choices are keyed (`Quiet` / `Primary` / `Destructive` for a button, `FieldLabel`, `FieldChrome`, `Reveal`). Colours are named in `Theme.xaml` — never write a hex literal into a trigger, which is how one "disabled grey" becomes three. **The last five were removed on 2026-09-22**, all in `Satellite.ConfigEditor`, all `#7E8899` — the same literal `BrandHeader` was extracted over, fixed there and left here, and **not** a long-hand `InkMuted` (`#98A3B2`) but a sixth grey belonging to no palette. Verified by capture on the five screens it appeared on: every changed pixel got **lighter**, none darker, none mixed, which is what says the text was recoloured rather than moved. Only `Theme.xaml` and `BrandLogo.xaml` carry hex now, where colours are defined — and one `#FFFFFFFF` in `Satellite.About`, left alone because that window has no form, the logo is its content, and pure white over the brand gradient may well be the decision rather than the drift.
- **The version lives in `Directory.Build.props`, and bumping it touches two more files it cannot reach.** The seven projects inherit `Version` / `AssemblyVersion` / `FileVersion` from there, but `src\AddIn.V20\Config.xml` and `src\AddIn.V21\Config.xml` carry `<AddInVersion>` and `<Product><Version>` written out by hand — the Publisher's schema wants the literal, and it is what TIA shows in *Options → Add-Ins*. Leaving those behind ships an Add-In reporting one version while the assemblies inside it carry another, which is worse than no version at all: the report a tester sends back is then wrong rather than missing. **`Product.Version` reads an attribute, never `Assembly.GetName()`** — an `AssemblyName` carries the code base, so asking for it demands `FileIOPermission` and throws inside TIA's sandbox exactly as `Assembly.Location` does; both measured in the restricted `AppDomain`. It also strips the `+<commit>` the SDK appends inside a git repo: useful in metadata, noise in a window.
- **`robocopy` reports success with a non-zero exit code** — 1 copied, 2 extras, 3 both; only 8 and above are failures. A script that does not normalise it prints success and returns failure to its caller. And **PowerShell 5.1 reads a UTF-8 file with no BOM as ANSI**, so every `.ps1` in `scripts\` stays ASCII: one accented character is a parse error. The same trap corrupts a document rewritten with `Get-Content | Set-Content` — use the Edit tool or Python instead.
- **A selectable row needs its own template, or Windows paints the selection.** `ListBoxItem` and `TreeViewItem` take their selected background from the **system** brushes — blue with focus, and a **pale box without it**, which on a dark form reads as a rendering fault rather than as a selection. Both are templated in `Controls.xaml` and paint selection in the brand colour, focused or not, via a `MultiTrigger` on `IsSelectionActive`. `ListViewItem` derives from `ListBoxItem` but **does not inherit its implicit style** — an implicit style matches the exact type — so all three are declared. A window that needs to add to one of them uses `BasedOn="{StaticResource {x:Type TreeViewItem}}"` rather than starting over.
- **A plain `ListBox` had no style at all until 2026-09-16, and the stock one paints white.** Every list in the framework had been a `ListView`, so only the rows were ever templated; the first real `ListBox` came out as `Ink` — light grey — on the stock white background, all but unreadable. `Controls.xaml` now carries an implicit `ListBox` style, and **`ListView` is untouched by it**: an implicit style matches the exact type, the same rule that already forces `ListBoxItem`, `ListViewItem` and `TreeViewItem` to be declared separately.
- **`ListView` and `TreeView` got theirs the next day, and the evidence was already in the repo.** Three windows — the data block snapshot, the coding-style report and the config editor — each wrote `BorderThickness="0" Background="Transparent" Foreground="{StaticResource Ink}"` on every one of them **by hand**, which is the shape of a decision made three times rather than once, and the fourth window that forgot got the stock white. Both are implicit in `Controls.xaml` now, `Transparent` because that is what all three chose. The inline copies still win over the style and are now redundant; they were left where they are rather than churn three verified windows for no visible change.
- **A `ListView` with a `GridView` ignores the implicit `ScrollViewer` style.** It asks for `GridView.GridViewScrollViewerStyleKey`, and the stock template draws the corner between the bars with a **literal** `White` that no resource override reaches — tried first, and the corner stayed white. `Controls.xaml` supplies that keyed style instead; keep its header row inside its own hidden-bar `ScrollViewer`, which is what keeps headers moving with the columns.
- **A `ComboBox` template must serve both `IsEditable` states.** A template written for the editable case has only `PART_EditableTextBox`, and a read-only `ComboBox` using it renders **empty** — the selection binds fine and nothing is drawn, because the stock template's `ContentPresenter` for `SelectionBoxItem` is missing. `Controls.xaml` now carries both and an `IsEditable` trigger picks one. The `ToggleButton` spans both columns and is declared **before** the editable `TextBox`, so a read-only combo opens from anywhere while an editable one still gets its clicks.
- **Theming a WPF input control takes a `ControlTemplate`, not `Setter`s.** Background, foreground, caret and selection are properties; **hover and focus are template triggers painting from hardcoded brushes**, so a styled field still flashes Windows-blue when touched. One `ControlTemplate` with `TargetType="Control"` serves `TextBox` and `PasswordBox` alike — both are `TextBoxBase`, which locates its editing surface by the name `PART_ContentHost`. Two consequences bite: an implicit `TextBox` style also lands on an editable `ComboBox`'s `PART_EditableTextBox` (so its padding must be zeroed against the combo's fixed height), and that same part is transparent by design, so a disabled trigger must dim the border and text but **never** repaint the background.
- **One file per type — every class, interface, enum and struct in a `.cs` of its own, named after it** (the maintainer's rule, 2026-09-22). `Core` had fourteen files carrying twenty-six more types than their names said — results, rows and enums tucked in beside whatever used them — while `PlcCoreLoadResult` next door had a file of its own, which is the inconsistency that raised it. **A private nested type stays inside its owner**: it is part of that type, not a second one. What the split turned up is worth knowing for the next one: **the `using` directives were checked by the compiler rather than by eye** — IDE0005 raised to a warning for one build and the `.editorconfig` removed after — and six were unneeded.
- **`AddIn.Shared.Assets.Open(path)` returns a `Stream`, never an image type.** The lookup is worth sharing; the type is not. `Adapters/Icons` materialises a `System.Drawing.Icon` for the TIA menu, and a WPF consumer would build an `ImageSource` from the same bytes. Keeping the lookup free of `System.Drawing` is what allows both.

## Naming convention (settled 2026-08-29)

| Project / folder | `AssemblyName` | `RootNamespace` |
| --- | --- | --- |
| `Core` | `PLC-Framework.Core` | `Core` |
| `AddIn.Shared` | `PLC-Framework.AddIn.Shared` | `AddIn.Shared` |
| `UI.Shared` | `PLC-Framework.UI.Shared` | `UI.Shared` |
| `S7PlcWebserverApi` | `PLC-Framework.S7PlcWebserverApi` | `S7PlcWebserverApi` |
| `AddIn.V20` | `PLC-Framework.V20` | `AddIn` |
| `AddIn.V21` | `PLC-Framework.V21` | `AddIn` |
| `Satellite.<Name>` | `PLC-Framework.Satellite.<Name>` | `Satellite.<Name>` |

The namespace says which layer a type is in: `AddIn.Shared.*` is version-agnostic, `AddIn.*` is version-specific.

**PascalCase throughout**, TIA version suffixes included (`V20`, `V21`). The version is not repeated in the namespace because the project name already carries it.

`AddIn` is spelled with a capital `I` everywhere — project, folder, namespace and class names — matching Siemens' own `Siemens.Engineering.AddIn`.

**One thing stays lowercase**, and it is not a style choice at all: the **`.addin` package extension**, which is what the Publisher requires.

**The repository, the folder and the solution file are `TIA-Portal-Add-Ins`** (2026-09-12). They were `tia-portal-addins` on a lowercase-kebab convention, and that convention lost its subject the day the public repository was created as `TIA-Portal-Add-Ins`: `git clone` writes *that* folder on every contributor's machine, so a lowercase solution inside it would be a mismatch nobody could fix locally. The rename went the way it did rather than the other because the repository name is the one that is published, linked to and typed by strangers — the cheap half to keep is the local one. Note the two differ by more than case (`addins` vs `Add-Ins`), so a clone is a genuinely different path and not a Windows case-folding curiosity.

> This replaces an earlier all-lowercase convention. Anything still written as `core`, `addin` or `.v20` is a leftover, not a deliberate choice.

Hyphens are legal in an `AssemblyName` and illegal in a C# namespace.

## Architecture decisions already made

Do not relitigate without new information:

1. **Three layers, decided by dependency set** — see below.
2. **Two Add-In projects**: `AddIn.V20` (valid V17–V20) and `AddIn.V21`. V21 breaks binary compatibility and splits the assemblies.
3. **Satellites are separate `.exe` files, and cannot be otherwise.** Verified: the Publisher **silently drops** any `.exe` listed under `AdditionalAssemblies` — no error, no warning, the package is just built without it. The filter is purely by extension (the same PE renamed to `.dll` is packaged), but that is no workaround: the part lands in `LocalAssemblyCache/` and TIA loads it as an assembly inside its own process, never as a file on disk. Siemens' own `Siemens.Engineering.AddIn.Utilities.Process` wrapper plus `ProcessStartPermission` confirm launching an external executable is the sanctioned path.
4. **Install location** — `C:\Program Files\PLC-Framework\`, exposed by `Core.InstallPaths.Root`, holding **every** executable shipped, satellites included, **flat**. **Per machine, not per user.** Its counterpart is `%LOCALAPPDATA%\PLC-Framework\`, `InstallPaths.UserRoot`, and the line between them is Windows' own rule: **`Program Files` is what the installer puts there, `%LOCALAPPDATA%` is what the applications write** — `.env`, `credentials.json`, `config.template.json`. **Not** next to the `.addin`: `UserAddIns` is per TIA version (V20 and V21 would each need a copy) and belongs to Siemens. **Not** derived from `Assembly.Location` either: TIA loads the Add-In out of the package, so that path cannot be trusted. `PLC_FRAMEWORK_HOME` overrides it for staging, and **`step2-deploy-vm.ps1` honours the same two rules** — an installer and an Add-In disagreeing about the root produce a "not installed" error on an install that looks fine. Installing needs elevation once; reading does not.
   - **This was `%ProgramData%\PLC-Framework\tools\` until 2026-09-11, and the move was a correction, not a preference.** The reason on record — *"`%ProgramData%` grants ordinary users read and execute but not write"* — is **false**: its `Users` ACE carries `Write` with `ContainerInherit`, inherited by every subfolder. Measured: a standard user creates a folder there, and a file inside it, unelevated. **A directory anyone can write to and everyone executes from is how a planted DLL gets loaded**, and default AppLocker rules deny execution outside `Program Files` and `Windows` for standard users, so satellites there would not start on a locked-down station. The move cost nothing — step 2 already ran elevated for V20's Add-In folder. The decisions built on the false premise (`.env`, `config.template.json` → `%LOCALAPPDATA%`) still stand, on the corrected reason: a user may *create* under `%ProgramData%` but not modify what the installer or another engineer wrote, the folder is shared, and the token is personal.
   - **`tools\` went with the move.** It earned its keep only while the root might hold data too; under `Program Files` the folder holds nothing but binaries, and `C:\Program Files\<Product>\app.exe` is the ordinary shape. Staging renamed to match: `.deploy\bin\`.
   - **`Root` reads `ProgramW6432` first, `SpecialFolder.ProgramFiles` second.** WOW64: `Core` is loaded into TIA (x64) *and* into the satellites (AnyCPU), so on a 32-bit host `SpecialFolder.ProgramFiles` would answer `Program Files (x86)` and the two halves would resolve **different installations** with nothing failing visibly. Verified the satellites are `ILOnly` with no `Preferred32Bit`, so this closes a trap rather than fixing a live bug.
   - **"Satellite" is a role, not a location.** A satellite is a WPF app the Add-In launches from the menu; it sits next to any command-line helper in the same flat folder. Splitting the folder by role was tried and reverted — it only invited arguments about which half a new executable belonged in.
5. **Add-In → satellite handoff: a JSON document over stdin** (chosen 2026-09-04). Siemens' `Process` wrapper exposes `RedirectStandardInput`, so the Add-In writes the payload straight into the child and no file is ever created — nothing to clean up, no permissions question, no stale handoff from a crashed run. **Verified end to end on the VM (2026-09-04): the redirection does survive the permission sandbox.** The satellite still reads the payload behind a small abstraction, and the fallback — a `%TEMP%` file whose path arrives as an argument — stays wired as reserve rather than as a bet. Not the TIA project folder: those are under version control, and tying the handoff to project writability makes a read-only project fail before the window even opens.
6. **Avoiding duplicates**: each satellite takes a named `Mutex` at startup, but *what* the name identifies differs by satellite, and the difference is the design:
   - `Satellite.About` — **one, full stop.** It shows the same thing to everyone.
   - `Satellite.DataBlockSnapshot` — **no guard at all.** Each run is a job with its own PLC, its own blocks and its own destination; a single instance would either refuse the second launch or silently discard the selection that came with it. The rule stands for satellites that show *state*; it does not for one that performs a *job*.
   - `Satellite.ConfigEditor` — **one per open TIA Portal**, keyed on its own parent process, falling back to one per file when started by hand. It edits a document, and two windows over one document lose each other's changes in silence.
   - `Satellite.CoreUpdater` — **one per project** (2026-09-19), keyed on the folder of the project it attached to, and **taken after the attach rather than at startup**, since that is the first moment the key is certain: a window started by hand learns its project only from the attach, the chooser may pick another, and the command line names a file where the attach names a folder. The config editor's reason with a project in place of a file — two windows would each compare a map the other is about to make stale and both write the same `repo\`, including the `stranded\` a move keeps its only copy in. **Not per TIA version**: V20 and V21 are two executables, but one folder is one `repo\`. A project never saved takes no guard — there is no folder to write into. The second window gives way having done nothing but attach.
   - `Satellite.CodingStyleReport` — **no guard**, for the snapshot's reason: each run is a report of its own selection at its own moment, and two side by side is how a before-and-after gets compared. **The window opens before the check runs, not after** (2026-09-15): a whole PLC takes long enough that an operator watching TIA sit busy with nothing on screen concluded the Add-In had died and restarted the machine. It is started with a `CheckingNotice` on its command line, says what is being checked, reads the handoff on a thread of its own so it keeps painting, and swaps to the table when the report lands. **Input closed with nothing in it is a message**: the check broke off, said in the window rather than left as a spinner nobody can interpret. It waits only when the notice *and* redirected input are both there — so a window started any other way, and an Add-In older than this window, behave exactly as before. **TIA says it is busy at the same time**, through `ExclusiveAccess` behind the `ITiaBusy` port: `IsCancellationRequested` is asked on every object and `Text` set every twenty-fifth, since one is a property read and the other a call into the host. **Cancelling sends no report** — closing the window's input with nothing is what says the check did not finish, and a report of the objects reached before Cancel would be one with a silent hole in it. A busy state TIA refuses is not a reason to refuse the check. **Import is offered only to a window TIA sent nothing to** (2026-09-13): a handed-over report is that run's result, and loading another workbook over it would contradict its own header. The reader finds columns **by header, not by position**, because a workbook opened and saved in Excel comes back with shared strings, inserted columns and sorted rows — all measured against the real Excel — and a failed import never replaces the report on screen. **A row says where it came from in three columns — PLC, software unit, object — rather than in one path** (report format 2, 2026-09-15): a project holds several PLCs and a PLC several units, each repeating the same folders and names, so a joined path could be read but never filtered, and a member row that does not name its object loses it the moment the table is sorted. The document writes `*` for the general program while the checker keeps "no unit" empty — one character is a presentation, and an empty cell then still means "this report does not say", which is what a format 1 workbook gives back. **Only the columns a row cannot be read without are required on import**, so those three arriving empty is not a refusal. **A member is checked by its own name, with the members it is declared inside in a column of their own** (report format 3, 2026-09-15): `Core.Checks.SimaticMlInterface` reads the exported SimaticML, where a `Struct`'s members are its children, and hands back `maxSpeed` with parent `motor` rather than the `motor.maxSpeed` the object model gives - which no naming rule can read. It brings `System.Xml` and `System.Xml.Linq` into `Core`'s references; both are framework assemblies TIA's process already holds, and the reader was run in the restricted `AppDomain` before it went anywhere near TIA. **Nothing in it knows a Siemens name**: it descends into a member's child `Member` elements and stops at a nested `Sections`, which is another type's interface - the same one rule that keeps a UDT's, a library FB's and GRAPH's `GRAPH_BASE` and `RT_DATA` contents out. **The Add-In gets the interface by exporting the object into `.plc-framework\tmp\coding-style-<timestamp>\` and deleting the file at once**, the run's folder going with it in a `finally` - what is in there is the project's own source, next to a versioned folder. **An object hands over a delegate rather than its members**, and the checker calls it only when the rules its name matched expect an interface, so a check costs what the configuration asks for rather than what the project contains: of five objects in the double, three were asked. **Nothing is ever compiled to make an export succeed** - TIA refuses an inconsistent block, and compiling it would change the project behind an operator who asked for a naming check; that refusal, a know-how protected object and a folder that could not be created are each one skipped row naming the object, and a source that throws is caught in `Core` so one block cannot end a check of thousands.
7. **No Siemens API exposes the Add-In's own path or the running TIA version.** Checked `TiaPortal` and the whole `Siemens.Engineering.AddIn` root namespace. Anything needing a location must derive it from a well-known folder.
8. **Satellites stay multi-file and stay on `net48` — for now.** A single-file `.exe` was considered on 2026-09-04 and deferred. ILRepack / ILMerge is ruled out outright: `App.xaml` merges its dictionaries by **pack URI, which carries the assembly name**, so merging breaks resource resolution at runtime with no build error. Costura.Fody does work and stays available. Worth knowing: **nothing binds a satellite to `net48`** — that constraint comes from Openness, which a satellite never touches — so multi-targeting `Core` and `UI.Shared` would give `PublishSingleFile` for free, at the price of a .NET runtime on the station. The real cost is the manual copy, not the file count, and the deployment automation already on the pending list fixes that for the `.addin` and the satellite at once.

### The three layers — this decides where every new type goes

A type's layer is decided by **what it depends on**, not by who happens to call it today:

| Layer | May depend on | Holds |
| --- | --- | --- |
| `Core` | only what **every** consumer needs | `Config` model + loader + **validators**, `Secrets` (`.env`, `${VAR}`), the `core.json` model (`Repo.PlcCore.Graph`), `InstallPaths`, `Product` |
| `AddIn.Shared` | `Core` + host types that are **not** Siemens | the Add-In's use cases (`Actions/`), its ports (`ITiaNotifier`, `IGroupNode`, `IProcessLauncher`, `ITiaBusy`, `HierarchyTargets`, `PlcSelection`, `Icons`), and the embedded `assets\` with their `Assets` loader |

| `S7PlcWebserverApi` | the network, and nothing of ours | the JSON-RPC client for a CPU's web server: `PlcClient`, `PlcVariable`, `PlcValue`, `PlcLimits` |
| `AddIn.V20` / `.V21` | anything, including Siemens | `AddInProvider`, `AddInController`, `Adapters/` implementing the ports |
| `Satellite.<Name>` / `Tool.<Name>` | `Core`, plus `UI.Shared` when it has a window | one executable each |

Verified from the compiled assemblies:

```
PLC-Framework.Core                -> mscorlib, System, System.Core, System.Runtime.Serialization,
                                     System.Xml, System.Xml.Linq   (the SimaticML reader),
                                     System.IO.Compression  (the core's .xlsx)
PLC-Framework.AddIn.Shared        -> mscorlib, PLC-Framework.Core, System.Core, System.Drawing,
                                     System.Runtime.Serialization
PLC-Framework.UI.Shared           -> mscorlib, System           (see below)
PLC-Framework.S7PlcWebserverApi   -> mscorlib, Newtonsoft.Json, System, System.Net.Http
                                     (no reference to Core)
PLC-Framework.V20                 -> + Siemens.Engineering.AddIn
```

**`UI.Shared` emits no reference to `Core` even though its `.csproj` declares one**, and no WPF reference either. Both are worth understanding rather than "fixing":

- The only thing it takes from `Core` is `Product.Title`, a `const string` — and a constant is **inlined at compile time**, so the dependency disappears from the metadata. The project reference still has to be there for the compiler, and `Core.dll` still has to travel next to the executable for everything else.
- Its WPF content is XAML, compiled to BAML resources rather than to code. `SingleInstance` is plain `Mutex` plus two `DllImport`s, which is `mscorlib` and `System`.

That is exactly why the layering is read from the metadata and not from the `using` statements: the answer is sometimes surprising, and only one of the two can be wrong.

**`S7PlcWebserverApi` deliberately does not reference `Core`.** It knows nothing about `Product`, `InstallPaths` or the config model, and keeping it that way is what lets it be exercised from PowerShell against a real CPU without dragging the rest of the framework in — which is how every one of its behaviours was verified. It is also why it must never go **into** `Core`: it pulls `System.Net.Http`, and `Core` is loaded inside TIA Portal's process.

**`UI.Shared` is named after the concern, not the consumer.** Anything with a window wants the logo and the palette, whether it is a satellite the Add-In launches or a command-line tool that shows a dialog. Naming it `Satellite.Shared` would have broken the rule above in the name itself. `AddIn.Shared` keeps its consumer-shaped name because its contents genuinely are Add-In vocabulary.

A useful consequence: **if a project references `UI.Shared`, it has a GUI.** The dependency states what a name prefix only suggests.

Consequences worth remembering:

- **`System.Drawing` must not reach `Core`.** `Core` is loaded inside TIA Portal's process, and its dependencies are the **intersection** of its consumers' needs, never the union. With `assets\` now in `AddIn.Shared` nothing in `Core` could pull it in — keep it that way.
- **Ports live with the layer whose vocabulary they speak.** `IGroupNode` talks about PLC group trees, so it belongs to `AddIn.Shared`, not `Core` — even though it has no Siemens reference.
- **`assets\` moved from `Core` to `AddIn.Shared` on 2026-09-04, because the transformation only ever serves the Add-Ins.** `Assets` sat in `Core` on the prediction that a WPF satellite would build an `ImageSource` from the same `.ico` stream. `Satellite.About` disproved it: it takes the logo from `UI.Shared/Resources/BrandLogo.xaml` as a vector for both the window and `Window.Icon`, and its executable icon is an `ApplicationIcon` resolved at build time — two uses of the same brand asset, neither through the loader. Turning a `.ico` into an image at runtime is TIA menu vocabulary, because `AddActionItemWithIcon` takes a `System.Drawing.Icon`; WPF wants vectors or Win32 resources. Moving it back means moving the glob with it, and would need a windowed app that genuinely reads an arbitrary asset at runtime — even then a XAML resource in `UI.Shared` is the likelier answer.
- Check the layering with the assembly metadata (`GetReferencedAssemblies`), not by reading `using` statements.

### `Satellite.DataBlockSnapshot` — settled 2026-09-04

Captures the current value of every variable in the selected data blocks, over the CPU's web server, and writes them to a workbook. **It is for settings and configuration that do not change**, not for live process values — which is what makes a sweep lasting tens of seconds an acceptable way to take a "snapshot".

- **Reliability beats speed, and they are mostly the same axis.** The read window *is* a data-quality property; shortening it was never about impatience.
- **Every variable that was browsed gets a row**, holding its value or the reason it could not be read. The Python app this was ported from drops the failures, which turns a partial capture into one that looks complete — the worst possible outcome here.
- **One file per data block**, named `<ip>-<DB>-snapshot-<timestamp>.xlsx`. A collision gets ` (n)` appended rather than overwriting.
- **A file is written only when the block read completely.** An incomplete read is reported in the window, with its reason, and leaves nothing on disk to be mistaken for a good capture.
- **Destination defaults to `<TIA project>\.plc-framework\exports\`**, editable. The project directory arrives in the handoff; `Core.Config.ConfigPaths` owns the literals so the Add-In and the satellite cannot drift apart. Check the folder exists and is writable *before* reading, not after thirty seconds of work.
- **Credentials are remembered per Windows user, keyed by project directory + PLC name,** in `%LOCALAPPDATA%\PLC-Framework\credentials.json`, with the password protected by DPAPI at `CurrentUser` scope. Written **only after the CPU has accepted them**, so a typo is never stored. The PLC address is an editable combo box filled from the project's own addresses. See the credential note below.
- **One PLC per instance**; several blocks of it per run. Several PLCs means several windows, which decision 6 now allows.
- **The blocks are the ones the Add-In passed, plus any the operator types.** A `+` and an `✕` under the list add and remove rows by name (2026-09-11), which is what makes the window usable started by hand — the mode the docs always claimed worked, and which in practice showed an empty list and a message sending you back to TIA Portal. That message now names both ways in.
  - **Still no browsing.** One call to the program root would list every block on the CPU, and that is deliberately not offered: the satellite would then be a block explorer with a capture button, and the Add-In's selection would stop being the thing that decides what a capture contains. Typing a name is a statement of intent; picking from a list of four hundred is a different feature.
  - **A duplicate is refused, case-insensitively** — it is one block on the CPU either way, so a second row would capture it twice and write two workbooks differing only by the ` (2)` a filename collision adds.
  - **Enter adds**, and the handler marks the key handled: otherwise it travels on to the window's default button and starts a capture, which is the opposite of what was meant.
  - **Remove stays disabled until a row is selected**, and re-selects a neighbour after removing, so clearing several is one click each.
  - **Two rows in separate grids line up with `Grid.IsSharedSizeScope` + `SharedSizeGroup`, never with a `Width`.** The `Block` and `Folder` rows share their label column and their button column, so both fields start and end at the same x at any window size. A constant width matches at exactly one: the field beside it lives in a star column that grows, and this window resizes from 660 upwards. Same lesson as the absolute margins in the connection grid.
- **Existence is always checked before capturing.** The block names come from the TIA project, and the operator may point the window at a different CPU.
- **Cancel acts between blocks.** Fine-grained cancellation would mean threading a `CancellationToken` through `BrowseDb` and `Read`; not worth it while a block is seconds.
- **The request timeout is a field in the window**, not a constant.
- Running with no handoff at all must keep working, with everything typed by hand. That mode is how every layer below the window was verified without TIA installed.

#### Remembering credentials — settled 2026-09-07

A capture session is an hour of launches, and retyping a web server password per launch is the friction that made this necessary. Four designs were rejected before this one, and the reasons are worth keeping because each looks reasonable until one fact lands on it:

| Rejected | Why |
| --- | --- |
| Windows Credential Manager | a second store to manage, and nothing else in the framework uses it |
| `.env` with `PLC_USER` / `PLC_PASSWORD` | **one TIA project holds N CPUs, each with its own user and password.** Two open projects, or ten CPUs in one, and a single pair is overwritten |
| the same pair in `config.json` | same defect, and `config.json` is versioned |
| reusing one window for several captures | decision 6 deliberately allows several instances; one window per PLC is the point |

**The mechanism came from the operator, and it is the better half of the design: the credentials are learned from use, not written by hand.** What changed was the location. The first proposal put `tmp.json` inside the TIA project, at `.plc-framework\tmp\` — but a TIA project is under version control (`.version-control\` sits right next to `.plc-framework\`), so a credential file there reaches a commit or a zipped copy sooner or later. Hence:

```
%LOCALAPPDATA%\PLC-Framework\credentials.json     per user, never versioned
```

- **Keyed by project directory + PLC name.** Both already arrive in the handoff, so the Add-In needed no change at all. The device name is the key rather than the address because a CPU can be readdressed and has several addresses anyway; the address is the fallback for a window started by hand, where no project handed a name over.
- **The password is DPAPI-protected at `CurrentUser` scope**, with application entropy so a blob from another program cannot be dropped in and decrypted. The blunt consequence: **it does not travel.** Another user, or another machine, gets nothing back and types the credentials again. That is the price of not having a shared key, and **a key baked into the `.exe` is not encryption but obfuscation — worse than plaintext, because it looks safe.**
- **Saved only after `client.Login()` succeeds**, never on clicking Capture. `CaptureRunner` takes an `authenticated` callback it invokes on the line after the login and nowhere else; the runner stays ignorant of credential storage. A wrong password is therefore never persisted, and never has to be un-persisted.
- **A *Remember* checkbox next to the password**, pre-ticked when something is already stored for that CPU. Unticking it and capturing **forgets** the stored entry — that is what unticking means. It starts unticked on a CPU never captured before: storing a password nobody asked to store is not a default worth having.
- **Nothing in the store throws.** A corrupt file, a blob written by another user, a missing directory: all return "nothing remembered" and the window opens normally. A credential cache that breaks the application it exists to smooth is worse than none.
- **The fields stay editable and show exactly what was loaded**, so the window looks the same as if the operator had typed it.
- **An eye reveals the password.** `PasswordBox` cannot show what it holds and its `Password` is not a dependency property, so the only way is a twin `TextBox` in the same cell with one of the two always collapsed; the eye swaps them and carries the text across, then moves the focus and the caret so typing does not fall into a field that is no longer on screen. Everything else asks `CurrentPassword()` rather than either control, so no caller has to know the value lives in two places. The icon shows a **struck-through eye while the password is on screen** — it states what is true now, not what clicking would do. Worth remembering when a credential is remembered rather than typed: revealing it is the only way to check *which* password came back.

### `Satellite.ConfigEditor` — decided 2026-09-08, phases 1 and 2 built 2026-09-09

Edits `config.json` with a UI. Launched from the menu by `ConfigEditorAction`, labelled **"Config. Editor"**. The contract it enforces is the README table; these are the decisions about the application itself:

- **Missing `.plc-framework\` or missing `config.json` is a normal state, not an error.** The window says so and offers to create one, folders included.
- **The template is `config.template.json`, embedded *and* on disk at `%LOCALAPPDATA%\PLC-Framework\`, and the operator chooses between them** (2026-09-13): *Create from system template* (the embedded one) and *Create from user template* (the file), the second always shown and disabled when there is no file. **This replaced "the file on disk wins", and the reason was found on the VM**: the editor writes that file itself, so a station that never touched it kept the template of whichever version first opened the editor, and every upgrade after was ignored in silence — a project created after the catalogue split came up with the old catalogue, no interface rules and no interfaces. Choosing explicitly makes the system template always the current contract and the user template a decision. Consequences: **no fallback** from one to the other, since the operator asked for that one; a user template that does not parse is **reported and left alone**, not replaced, and the panel stays so the other button is one click away; creating from the system template still leaves a copy **only when there is none**, so there is something to customise, and it says so; **Revert on a never-saved document goes back to the template it started from**, not to whichever the editor would pick. Seeded from the `config.json` in `.example\`. **Per user, not the install folder** — that was the first plan and it carries the same defect as the old `.env`: the install folder is `Program Files`, where ordinary users have read and execute but **not write**, so the self-repair would work on a developer's machine and fail on a real station. Anything this satellite *writes* goes to the per-user folder; `Program Files` is for what the installer puts there.
- **One instance per running TIA Portal**, and the satellite works that out **by itself**: it reads its own parent process, which is TIA because `ProcessLauncher` starts it with `UseShellExecute=false`. **The Add-In cannot supply the PID** — measured in the restricted `AppDomain`, `Process.GetCurrentProcess()` throws `SecurityException` under partial trust, for `Id` and `ProcessName` alike, and `AddIn.Utilities` holds only `Process` and `ProcessStartInfo`, neither of which offers it. Reading the parent costs ~170 ms once at startup, cannot be forged by editing the handoff, and degrades correctly when started by hand: no TIA parent, no tie. The mutex name hashes it — `SingleInstance.Claim` builds `Local\<Product>.<appId>`, and a backslash **separates the mutex namespace**, so no raw path can go in there.
- **`Newtonsoft.Json` for reading and writing**, in the satellite only — `Core` keeps `DataContractJsonSerializer`, which is fine for loading but wrong for saving: it does not indent, it orders members its own way, and a read-write round trip **drops every key the model does not know**. This file is meant to be hand-edited, so edits are surgical over the JSON tree, leaving untouched anything the editor did not change.
- **The GitHub token never enters `config.json`.** The file always carries the literal `${REPO_TOKEN}`; the secret goes to the `.env`, which lives at **`%LOCALAPPDATA%\PLC-Framework\.env`** for two reasons — the token is personal, and the install folder is not writable by ordinary users, so an editor saving there would work here and fail on a real station. The field is masked with the same show/hide twin-control as the PLC password.
- **`provider` is a drop-down at the top of the Remote section** (2026-09-22), holding one item today and a drop-down all the same: the set is closed, so it is chosen rather than typed — which is what makes a second host a line in the editor instead of a class of typo to validate against. It comes **first** because every field under it is read through that one. **Absent in the file shows as `github`**, and a value the set does not hold is added and shown as it is, exactly as `coreSource` does — blanking it would let the next edit anywhere on the form write a decision nobody made over somebody's typo, where the validator names it and `Save` stays off. **It is written only when the remote section already exists**, the token's rule rather than the fields above it: those write back empty and `ConfigDocument.Set` creates nothing on the way to removing, while a provider always has a value and would plant the whole section around itself in a purely local configuration.
- **The validator came first**, and it was the right order: it is `Core`'s, this satellite is its first consumer, and the Add-In needs it too.

#### Hierarchy — phase 3 built 2026-09-09

**Seven trees, not four**: the four top-level concerns plus three inside `softwareUnits`. One `TreeView` serves all seven — the tab decides which array it is bound to — because seven tree views would be seven copies of the same twenty lines.

- **Add, rename and remove. No moving**, decided deliberately: the folder names carry numeric prefixes (`00-OB`, `01-FSL`) and TIA orders them by name, so a reordering gesture would cost real work to change nothing anybody sees.
- **A duplicated name is marked red on the node itself**, and on *both* offenders, while typing. The validator already reports the path; in a tree the position is what makes the mistake obvious. Case-insensitive, because "core" and "Core" are the same folder to anybody reading it.
- **`softwareUnits` is optional as a whole**, so the section can be added or removed entire — and it is added with all three of its lists, because the contract requires every one of them once the section exists. Removing it throws away folders somebody built, so it is **the only confirmation prompt in the window**, and it earns it.
- **Removing the last child drops the `groups` key** rather than leaving `[]`. `groups` is optional and most folders are leaves; an empty array would be noise that means nothing.
- **`GroupNode.ToString()` returns the name, and that is not decoration.** A `TreeViewItem` takes its **automation name** from the bound object's `ToString()`, so without it every node announced itself as `Satellite.ConfigEditor.Editing.GroupNode` — to a screen reader as much as to a test. The `TextBlock` in the template is what the eye sees; `ToString` is what everything else sees.

Verified against the real config: eleven root folders and their children loaded, renaming `03-ALL`, a deliberate duplicate blocking `Save` with `blocks[3].name` named in the footer, adding a sub-folder, and both software-unit lists. The saved file kept `codingStyle` and its 15 rules untouched.

#### The window — phase 1 built 2026-09-09

Section navigation down the left, not tabs: two of the sections subdivide again, and nested tabs stop being readable. A **dot beside a section** says that section has problems, which is exactly how the validator already reports them — per concern.

- **Structural problems block saving; environmental ones never do.** A configuration prepared here for another station is not wrong because a drive is not mapped on this one, so those are shown as warnings. `Save` is simply disabled while the structure is broken.
- **A file that exists but does not parse is never offered the template buttons.** Either would overwrite it, and a file somebody broke by hand is still a file somebody wants back. It shows the parser's line and column instead.
- **Both repository sections stay visible and editable**; every one `coreSource` does not select is dimmed — both, when it is `none`. A project often carries both and switches between them, and hiding the other one makes it look lost. `none` is the drop-down's word for a JSON `null`, **written explicitly** so the file shows a decision rather than an omission; a value outside the set is shown as it is rather than left unselected, because the next edit anywhere would otherwise write the selection back and turn a typo into "no repository".
- **`ConfigDocument.Set` never creates on the way to removing.** The form writes every field back on each change, and creating the parents of an empty value planted empty repository sections — then a token reference inside them — in files that had none.
- **Creating from the template writes nothing until Save**, so backing out costs nothing.
- **`ConfigLocation.Resolve` accepts all three ways of naming a project**: the project folder, the `.plc-framework` inside it, or the `config.json` itself. Appending the convention to whatever was picked is wrong the moment somebody picks one step deeper — which is the natural thing to do, since `.plc-framework` is the folder with the file visibly in it. It produced `…\.plc-framework\.plc-framework\config.json` and a window reporting "no configuration" on a project that had one. It is **shared with `App`** rather than private to the window, because the single-instance guard keys on the same path: two ways of working it out would let two windows open one file each believing it was alone.
- The token uses the same twin-control eye as the PLC password, and writes to the `.env` **before** the JSON: there is no point leaving a `config.json` behind that references a variable nobody managed to set.
- `Hierarchy` still shows a panel saying it is not editable here yet, and that saving leaves it untouched — which is true, and is what the JSON-tree editing buys.

#### Coding style — phase 2 built 2026-09-09

Three tabs inside the section: **Object rules**, **Interface rules** and **Applies to**.

- **The two catalogues share one area** (2026-09-13): the tab decides which the list shows, since a rule's id, pattern, "Try it" and description are the same in either. Each tab remembers its own selection. A hint beside the tabs says what the visible one is for, because the difference between the catalogues is the design and nothing else on screen states it.
- **Ids are unique across both catalogues**, in the editor as in the validator: adding picks a name neither uses, and renaming onto the other catalogue's id is adjusted (`function` → `function_2`) rather than left to fail. Renaming an interface rule rewrites every interface section naming it.
- **Removing an interface rule removes a section it leaves empty, and an interface it leaves empty.** A section implementing nothing is invalid, so keeping it would block Save over what the operator just did on purpose — and a section no rule covers is not checked, which is what removing it says. A **type** left with nothing to implement is kept instead: its row is on screen to be fixed. The last interface rule removed takes the optional `interfaceRules` key with it.
- **Reading the interface catalogue never creates it.** The object catalogue is required and is created on first touch; an optional list planted by opening the section would change what the next save writes.
- **The status line is set after `Revalidate`, never before** — `Revalidate` rewrites it, which is how "'x' was already taken" had never once been seen.
- **An object rule's interface is edited in its detail**, below "Try it" (2026-09-13): one row per section, a drop-down of the eight sections (the free ones plus its own), the interface rules it answers to as tags, and a `+` offering only interface rules. **The rows are `TypeRow` and `AppliesSection` again**, fed the eight sections and the interface catalogue: a section is the same `{type, implements}` pair as a type, and a second implementation of "tags from a catalogue, drop-down from a closed set, no duplicates" would drift from the first. Core keeps the two apart because there the vocabulary is what gets validated; here the closed set arrives from outside, so neither row can offer the other's values. The tag is one `RuleChip` template shared by both lists.
- **"Add section" is disabled while there are no interface rules**, saying why: a section with nothing to answer to is invalid and its `+` would offer nothing. Removing the last section drops the `interface` key — absent already means "not checked".
- **The rule detail scrolls at small sizes, and its grid takes the viewport's height with a floor** (`Height` bound to `ViewportHeight`, `MinHeight` 400). A plain `ScrollViewer` hands its content infinite height and turns star rows into `Auto` — the trap recorded below — whereas this keeps the interface and the description sharing the height at any size and scrolls only when the floor is reached. Measured by capture, not assumed: at the minimum size, before it, the interface showed half a row and the description none at all.
- **A section row puts the drop-down and the tags in one `WrapPanel`**, so the tags drop to the next line when the row is narrow. In columns of their own they were cut to "varia" at the minimum width. For the same reason the hints beside the tabs and beside "Interface" are one trimmed line with the sentence in the tooltip: wrapped, the tab hint ran to four lines and took the detail's height.

- **`implements` shows only what the type implements, as tags with a cross**, and a `+` offers the rules it does not have yet. Never a text field: building the choice from the catalogue makes a dangling reference *impossible* rather than merely detectable — half of what the validator exists to catch, removed at the source. The `type` comes from a drop-down of its section's closed set, which removes the other half.
  - Tick boxes were tried first and were wrong: fifteen rules across ten types is a hundred and fifty controls, nearly all empty, and the noise hides the one thing worth reading. A tick box that *disappears* when cleared would also behave like nothing else in Windows.
  - **A reference to a rule that does not exist is shown in red, not hidden.** With boxes built from the catalogue there was no box to clear, so the editor could report that problem and not repair it — which is the wrong half. As a tag, removing it is one click, and `Save` unblocks itself. Verified against a file doctored to hold one.
  - Written back in **catalogue order, with anything unrecognised kept at the end**: the file must not change because two people clicked in a different sequence, and a dangling reference has to survive a save so it can be seen and removed rather than silently dropped.
- **Renaming a rule carries its references with it.** `CodingStyleEditor.RenameRule` rewrites every `implements` entry; without that, renaming breaks four places silently and at a distance. It also refuses to collide, appending `_2` rather than leaving the validator to complain afterwards. Committed on **leaving the field**, not per keystroke: an id is a key, and rewriting references on the way from `type` to `typeName` would churn the document through a dozen half-typed names.
- **Removing a rule removes its references too**, for the same reason.
- **The pattern reports whether it compiles, and a "Try it" box says whether a sample name matches.** A regex that compiles can still be perfectly wrong, and today that is only discovered when the Add-In marks half a project. Verified: `OB_MAIN` matches the interrupt rule, `ob_main` and `OB_` do not.
- **A new rule gets `^$`, which matches nothing.** An empty pattern matches *everything* — a naming rule that approves every name ever written.
- **No `ScrollViewer` wraps the whole section, and that is deliberate.** One there hands every panel infinite height, so a `*` row inside behaves like `Auto`: the rule list grew without end and pushed its own Add/Remove buttons off screen. Each panel now brings the scrolling it needs — the list scrolls inside itself, the description takes what height is left and scrolls, and the buttons stay put. Checked at the window's minimum size, where the list drops from 556 px to 345 and nothing goes off screen.
- **A hint under a `*` field competes with it for the last of the height, and wins.** The "one line each" note left the description two lines tall with the note overlapping it; beside the heading it costs nothing.
- **Tick-box labels are a `TextBlock`, not `Content`.** WPF reads `_` as a keyboard accelerator and hides it, so `data_container` rendered as "datacontainer". An id is an exact key; it has to read exactly. Same for a `MenuItem` header.
- **A type appears at most once per section.** A second row for the same `type` says nothing the first does not — the pairing with its rules is already complete — and only raises the question of which one counts. So a type in use is offered **nowhere it could be duplicated**: "Add type" lists only the free ones and disables itself when there are none, and each row's drop-down holds the free ones **plus its own**, without which the row could not display the value it already has. `AppliesSection.Refresh` recomputes both after any change, and the section wraps the callback so the window cannot forget to ask.
- **The drop-down lists are updated in place, never cleared and refilled.** A `ComboBox` whose `ItemsSource` empties loses its selection, and the row would come back blank — which then writes an empty type into the document.

**Verified end to end**: opening a real config, the empty-project and broken-file states, creating from the template, and saving. The saved file kept all 15 rules with their descriptions, the 11 block groups and the four root keys in their original order, and Core loads and validates it clean.

`ConfigEditorAction` puts it on the **project root** of both Add-Ins, labelled **"Config. Editor"**, and deliberately does **not** check that `config.json` exists — its absence is the case the editor is most useful for. It carries its own `ConfigEditorPayload` rather than reusing `HandoffPayload`, which would send a null `plc` and a null `dataBlocks` on every launch. All five paths exercised with doubles, and the payload serialised **inside a restricted `AppDomain`** — a new data-contract type is exactly what partial trust rejected once before.

### Sharing code between `AddIn.V20` and `AddIn.V21`

Three mechanisms, each for a different case:

| Situation | Mechanism |
| --- | --- |
| Code that **diverges** between versions | port in `AddIn.Shared` + one thin adapter per version |
| Identical code with **no** Siemens dependency | put it in `AddIn.Shared` — one binary serves both |
| Identical code **with** Siemens dependencies | must be compiled twice; a shared assembly is impossible |

That last row is not a preference: `Siemens.Engineering.AddIn` (V20) and `Siemens.Engineering.AddIn.Base` (V21) are **different assembly names with different public key tokens**, and V21 does not ship the V20 one. A shared binary would bind to one identity and fail to load in the other host. Source linking is the only option there; today `AddInProvider.cs` and `TiaGroupNode.cs` are simply duplicated instead.

**`Siemens.Engineering.AddIn.Utilities` is the subtler case, and the one worth remembering.** Its `Process` wrapper has an identical public surface in both versions — same namespace, same type, same members — but the assembly carries a **different public key token** in each: `65b871d8372d6a8f` in V20, `29bfe5fdf4ba5d3b` in V21. Source-identical code still cannot be compiled once. That is why `Adapters/ProcessLauncher.cs` is duplicated behind `IProcessLauncher`: the two files are byte-identical and nothing in them hints at why, so the reason lives here.

`#if V20 / #if V21` remains rejected: it degrades fast and makes menu code unreadable.

### Shipping `Core` — settled, do not relitigate

`Core` and `AddIn.Shared` travel inside each `.addin` via `AdditionalAssemblies` in `Config.xml` — **one entry per assembly; transitive project references are not packaged automatically**. **Do not propose merging the DLLs** with ILRepack or Costura.Fody: the `.addin` is already a single deployable file, `AdditionalAssemblies` is the vendor-supported mechanism, and the satellites will need `Core` as an assembly with one identity anyway.

### Exporting a project's objects — `Core.Exports.ExportTree`, 2026-09-15

- **A mirror of the project tree, not a folder per run.** `exports\<PLC>\Program blocks\03-ALL\_oc_seq2.xml`: exporting again writes over the same files, so `git diff` between two exports says what changed in the *project*. A timestamped folder, which is what the snapshot does, keeps history nobody can compare without work — and the two live side by side in `exports\` because they answer different questions.
- **The folder names are TIA's own**, so the tree reads like the project tree. The price is that they follow the interface language, and changing it renames every folder. The one level that is ours and never translated is `Software units`, because finding a unit's objects must not depend on the language the project was opened in.
- **A name Windows will not take is changed and marked**, and the mark is eight hex digits of the original name: `DB:1` → `DB_1~0f3a25be`. Two names TIA keeps apart must not become one file — `DB:1` and `DB_1`, `block.` and `block`, and the device names `CON` and `COM1` that no file may carry. **The mark comes from the name, never from the order objects were reached**, so the same project exports the same file names every time and a diff shows the project rather than the run. A name Windows already accepts — accents and `ß` included — is left exactly as it is.
- **`GetHashCode` is not used for that mark.** It is not promised to be stable from one run to the next, and a file name that moved between exports would turn every diff into noise. FNV-1a, written out, is six lines and nothing here is a secret.
- **A path over 259 characters is reported, not attempted.** It is the one limit an engineer meets by accident — a project inside a user profile, a TIA tree four folders deep, a long block name — and the failure it produces otherwise names nothing anybody can act on.
- **The export keeps more than the coding-style walk does, and the difference is the question being asked.** A naming report drops what TIA named itself, because a rule could only fail it; an export is the project's program, so **instance DBs, array DBs and technology objects are all written**. Out stay only the system folders and the default tag table, which TIA rebuilds. **`ExportOptions.WithDefaults`** for the same reason: this is the copy somebody restores from, where the coding-style check's throwaway export takes `None`.
- **No window: TIA's own notification says how many, where, and what would not come out.** The result is files on disk, and a window would exist only to be closed. **Every refusal is named** — an export that quietly skipped four blocks is a backup with four holes in it — and **a second object landing on the same file is refused rather than allowed to overwrite the first**. Cancelling stops there and says so, keeping what was already written: deleting it would throw away a previous export that is still on disk.
- **Every format TIA offers, not just SimaticML** (2026-09-15, asked for outright: *"Necesito la exportación completa en todos los formatos"*). SimaticML is what everything has and what an import restores from; beside it go the SIMATIC SD pair and the language source, and **which of those exist is decided by `PlcBlock.ProgrammingLanguage`** rather than by us — LAD and FBD get SD, SCL adds `.scl`, STL has a `.awl` and no SD, GRAPH has neither, a DB adds `.db`, a PLC data type adds `.udt`. The table is in [openness-notes.md](docs/openness-notes.md); the reason it is a table rather than a rule is that TIA's own dialog offers exactly that and nothing derives it.
- **An object is therefore several files, and "it came out" stops being a yes or no.** `ExportOutcome` carries a file count and a problem, so a block whose SimaticML was written and whose source TIA refused is neither a success nor a failure: the notification lists *came out without every format* apart from *were not exported*, and reporting either as the other would mislead somebody reading the export as a backup. The count in the summary is files, not objects, because that is what is on disk.
- **`ExportAsDocuments` reports failure in its return value, and it is the only export call that does.** It answers a `DocumentExportResult` with `State` — `Success`, `PartialSuccess`, `Failure` — and the `FileInfo`s that really came out, so **a clean return can mean nothing was written**. Counting the pair as two files would have put a refused SD export in the summary as two files on disk; the files are counted from `ExportedDocuments` instead and TIA's own messages are what the problem says.
- **A source is generated through the external source folder, and through the software unit's own when the object lives in one.** `PlcExternalSourceSystemGroup.GenerateSource`, with `GenerateOptions.None` — never `WithDependencies`, which would pull every called block and data type into each file and write the same code a hundred times, turning the diff this export exists for into noise.
- **A safety PLC data type is attempted and its refusal reported, because nothing can tell one apart.** `PlcType` carries no language and `Siemens.Engineering.Safety` declares no data type — both checked rather than assumed. So an F-UDT comes out with its SimaticML and its SD pair and is listed as having come out without every format, which is *true*; guessing from a name would have been a rule about Siemens vocabulary inside a binary, which this project has already refused twice for the coding-style check.
- **The path limit is checked against the longest extension an object could produce**, `.s7dcl`, not against the first file written — otherwise a name that fits its `.xml` and not its SD pair would be half-exported and reported as whole.
- **The alarm text lists are one workbook per PLC, and Openness leaves no choice.** `PlcAlarmTextlist` has no `Export`; the only way out is a service that writes a PLC's lists into one `.xlsx`. Its filtered overload narrows **by name**, and a unit's list can share a name with the PLC's, so a file built that way would mean something different depending on where the export was started — `exports\<PLC>\Alarm texts.xlsx` always means the same thing. A PLC without the service says so and the rest of the export carries on.
- **Both walks share `TiaProjectPlaces`.** The report's PLC, unit and folder columns and the exported folders are the same answer to the same question, and two copies of that walk would drift the first time one learned about a new kind of folder.

### Updating a project's core — `Core.Repo`, stage 1 built 2026-09-16

The core is the maintainer's own library of blocks, kept in a separate repository (`code`, not public, beside this one) as `.scl`, `.udt` and `.xlsx` sources under `plc/<family>/core/`, with a **committed** `core.json` beside them that a Python generator writes. This is the framework reading that, comparing it with what a TIA project actually holds, and eventually offering to close the gap.

- **`core.json` is the source of truth, and the maintainer settled it in those words**: a file under the core folder that the graph does not list **is not part of the core**, whatever it looks like. So nothing walks the folder to discover nodes — the graph is the list, and the folder only answers where a node's source sits. That is what keeps `system-v3.0.xlsx` and `jxc-alarm-list-v1.0.xlsx`, which are in the folder and not in the graph, out of every comparison without a rule naming them.
- **The core's graph is always copied into the project, as `.plc-framework\repo\core.json`, and compared from there**, never read from the repository in place. A comparison against a repository that moves on describes a core nobody can point at afterwards; with a copy, both halves of every result are on disk side by side for as long as the project keeps them. `repo\` also holds `project.json` and the `tmp\` a download writes, which is why its layout is `Core.Repo.RepoPaths` rather than one more name in `ConfigPaths`.
- **Until 2026-09-22 the copy was the whole core folder, mirrored into `repo\core\`** — every source, in every project, on every Load, for a comparison that reads one file. It is gone, and so is the guarded removal a mirror needs; see *A Load copies the graph, and a download its own sources* below.
- **A block is matched to the core by its base name, and that is safe because it was measured.** `base` equals `name` on all 264 nodes of the real core, so the TIA symbol a project block carries *is* the node's base and the join needs no heuristic. `PlcCoreValidator` reports the day that stops being true, because a node whose `base` and `name` differ cannot be found by the name a project uses.
- **Several current versions of one block is legal, and a validator rule saying otherwise was written and removed the same hour.** Nothing in the format's contract says one base has one current version, and the generator already reports the case that genuinely breaks: an **unversioned** dependency that could mean either, as `ambiguous-dependency`. So `PlcCoreCatalog.Currents` hands back all of them and `Current` answers null for "do not decide this here", which is the choice the operator makes when picking what to import.
  - **The example this was argued from has since gone, and the decision stands without it** (measured 2026-09-17, on a `core.json` generated the day before). It used to say `_mc_positioning1Axis` carried v1.0, v1.1 and v2.0 all current on purpose; the repository has since been tidied into a chain — v1.0 and v1.1 `deprecated` behind v2.0 — and **today the whole core is exactly one current per base**: 264 nodes, 247 current, 247 distinct bases, and all 17 deprecated ones naming their replacement. That is a fact about one snapshot, not a contract, which is why the rule was not put back: a validator that demands it would fail the day two majors go live again, and the maintainer chose the tolerant reading for stage 4 on exactly that ground.
- **The graph is validated on this side even though the generator validates it too**, and that is not duplication: `core.json` is a committed artefact that can be stale, hand-edited, or from a repository this machine does not control. Trusting the `reports` array *inside* a file to describe that same file is trusting the thing being checked. Its issues are `ValidationIssue`s, the config validators' own type, so one window shows both.
- **An edge's `to` is only checked when the edge says it resolved.** 147 of this core's 296 edges are external — Siemens system blocks and things tracked elsewhere — so demanding a node there would report half the graph as broken. An edge *claiming* it found its target, in a graph that no longer holds it, is the half that means something.
- **Resolving a repository path is structural; whether it exists is not.** `LocalSource.Of` builds the paths and never touches the disk, `Exists()` asks separately — the same line `EnvironmentValidator` already draws, for the same reason: a configuration prepared for another station is not wrong because a drive is not mapped here. Note `folder` is written with forward slashes (`plc/s7-1x00/core`) in a file Windows resolves, and a node's `file` is relative to the **repository root** rather than to the core folder, so stripping one prefix from the other is what turns a node into a file on disk.
- **The Add-In entry lives at PLC level only** (2026-09-16, the maintainer's decision): not on the project, not on an object. A core belongs to one PLC's software, so an entry on the project root would have to ask which, and one on a block would offer a whole-PLC operation from a single object.
- **The satellite will hold Openness itself** — see the next section — so this layer is written for full trust *and* checked under the tightest partial trust anyway, because `Core` ships inside the `.addin`. Measured in an `AppDomain` granted `Execution` alone: the graph parses, validates and answers its lookups. `Path.GetFullPath` demands `FileIOPermission` there and is caught, which is why resolving a repository returns a sentence rather than throwing.

### `Satellite.CoreUpdater` — a satellite that holds Openness, stage 2 built 2026-09-16

The first satellite that talks to TIA Portal itself, and the decision that makes the core update a satellite rather than an Add-In. **The maintainer proposed it** — *"podemos valorar que este Satellite use openness para poder leer y escribir en el proyecto"* — and the reflection agrees: `TiaPortal.GetProcess(int, TimeSpan)` and `TiaPortalProcess.Attach()` exist, identically, in both versions.

- **Three projects for one satellite.** `Satellite.CoreUpdater` is a **library** holding the window and an `ITiaSession` port; `…V20` and `…V21` are thin executables with a `Main`, an assembly resolver and one adapter. Not a preference: `Siemens.Engineering` (V17–V20, token `d29ec89bac048f84`) and `Siemens.Engineering.Base` (V21, token `29bfe5fdf4ba5d3b`) are different assemblies, so a single binary binds to one and fails to load in the other — the same rule that already duplicates `ProcessLauncher`, applied to a whole application. Checked in the built output: the library references no Siemens assembly, and each executable references exactly one.
- **The Add-In hands over nothing at all.** Every other satellite is told what to work on because it cannot ask; this one attaches and finds the project itself. That removes the payload type, the handoff, and the whole class of bug where the two ends disagree about what was selected. The Add-In entry is one line that launches an executable.
- **The Add-In cannot pass its own PID even if it wanted to**: `Process.GetCurrentProcess()` throws `SecurityException` under partial trust, measured in a restricted `AppDomain`, and `AddIn.Utilities` offers only `Process` and `ProcessStartInfo`. That much still stands — **but the conclusion drawn from it did not**, see the next bullet.
- **The satellite recognises its TIA Portal by the project, not by the process that launched it, and the first version had it the other way round** (2026-09-16). The reasoning was that an Add-In runs inside TIA Portal, so the parent process *is* the instance to attach to. On a station with two open, in **both** TIA versions, the parent is in neither list: V21 parent 12896 against portals 12924 and 5236, V20 parent 14736 against 7756 and 2480. TIA either hosts the Add-In in a process of its own or starts the child through an intermediary, and **which of the two is still not settled** — that it does not matter is the point of the fix. **It survived until somebody opened two instances** because a lone TIA Portal is taken without consulting the PID at all, which is exactly the shape of bug a short-circuit hides. The Add-In now passes the open project's own file as a third argument and the satellite matches `TiaPortalProcess.ProjectPath`: the Add-In is *in* a project, so that is the one fact both ends name identically. The ancestry survives as a second signal — **the whole chain now**, since an intermediary's own parent would still be TIA — and it is read on the worker's thread, because one WMI query per level before the window paints is what a satellite that failed to start looks like.
- **With one TIA Portal running it attaches; when nothing names one it asks.** Guessing would attach to somebody else's project and then offer to change it — so the refusal stands, and the same list it was already printing became the choice. **Each signal must name exactly one instance**: the same project open twice, or a chain running through both, identifies nothing, and taking the first would be the guess again. **Nothing is preselected in that list**, for the same reason one level up: a highlighted first row turns *Attach* into one click on whatever was at the top. The window lists what was running either way, because "none" and "several, and not that one" read alike and want opposite answers.
- **An older Add-In keeps working**, which is what fixed the arguments rather than the payload: two arguments still parse, blank and absent are read as the same thing, and a project that was never saved sends an empty third argument so the positions stay fixed whatever is known.
- **The attachment is not kept.** Openness objects belong to the thread that obtained them, so *holding* one means deciding where that thread lives and how the window talks to it. Nothing needs a live session yet, and a snapshot has no thread to be wrong about — **stage 3 decides the threading model**, and it is the first thing it has to decide.
- **Disposing an attached `TiaPortal` closes TIA Portal, and this file said the opposite for a day.** The first version wrapped it in a `using`, on the reasoning that disposing an *attached* portal detaches the client — and that reasoning was written down here as though it had been measured. **The VM settled it**: the V20 instance shut down, with the engineer's project open, the moment the window said "Ready". `TiaPortal.Dispose` is how an Openness client *shuts a portal down*, and attaching does not change what the method means. **Nothing is disposed now** — not the portal, not the process handles. What is held is a handful of handles in a process that ends when its window closes; set against closing somebody's TIA Portal, that is not a trade worth thinking about. The lesson is older than this bug: **"it detaches rather than closes" is a claim about behaviour, and belongs on the VM's side of the line this file draws in its own header.**
- **An Openness client has to find the assemblies itself**, and that is the one real cost of moving off the Add-In: they are not in the GAC, not beside the executable, and only the installation knows where they are. `OpennessAssemblies` reads `HKLM\SOFTWARE\Siemens\Automation\Openness`, matching loosely because value names differ between installations. **Installed before any Siemens type is touched**, which one method boundary marked `NoInlining` is what guarantees — a `Main` naming the adapter would resolve it while being JITted, before its own first line ran.
- **One TIA installation publishes every older API it serves, and taking the first was a real bug.** `20.0\PublicAPI\` holds `17.0.0.0`, `18.0.0.0`, `19.0.0.0` *and* `20.0.0.0`, each publishing its own `Siemens.Engineering` with a path. Enumerated as the registry returns them the first match is **V17**, which loaded and then failed on the first type V17 does not have: *"Could not load type `Siemens.Engineering.SW.Units.PlcUnitBase` from assembly `Siemens.Engineering, Version=17.0.0.0`"* — software units did not exist yet. The subkey named after the version this was built for goes first now, then the rest newest-first. A station with only an older TIA still resolves, and fails where it uses something that TIA has not got, naming the type.
- **The window says V20 or V21 beside its title** (the maintainer asked for it): one binary per version is what Openness forces, the two are otherwise identical on screen, and an operator with both installed had no way to tell which one an Add-In had opened for them.
- **The registry publishes V20 and not V21**, which is the shape of the whole resolver and was read off the VM rather than guessed. `Openness` holds `20.0`, `21.0` and `AllowList`; `20.0\PublicAPI\` carries a subkey per API it still serves — 17, 18, 19, 20 — each publishing `Siemens.Engineering` and `Siemens.Engineering.Hmi` with their paths; and **`21.0\PublicAPI\21.0.0.0` publishes `EngineeringVersion` and nothing else.** No path, no assembly, nothing to take a folder from. So V20 resolves by name and V21 has to derive: what V20 *does* publish is the layout — `…\Portal V20\PublicAPI\V20\Siemens.Engineering.dll` — and the same installation root with the version segments rewritten is where V21's assemblies are. **The root comes from the machine rather than from a hardcoded `C:\Program Files`**, so a station that installed TIA elsewhere still resolves; `%ProgramFiles%` is only the last resort. `net48` is probed under each candidate too, since V21 puts its sixteen assemblies in a framework subfolder that V20 has no equivalent of.
- **That layout was found in one run because the failure path prints where it looked**, and it is the thing worth carrying out of this stage. A registry layout cannot be checked on a machine without TIA Portal, and a resolver that only answers "not found" turns every wrong guess into another day; one that reports which keys existed, what each published and every folder probed turns the same round trip into an answer. **Confirmed attached in both versions afterwards.** The panel scrolls, too — the first version centred it in a fixed row and the VM clipped off exactly the half that said where it had looked, which is a diagnostic defeating itself.
- **No `App.xaml`.** An `ApplicationDefinition` generates a `Main`, which would have to live in one assembly. **So the window merges the brand dictionaries itself**, in its own `Window.Resources`, by the same pack URIs — which carry the *assembly* name. They were merged into `Application.Resources` in `CoreUpdaterApp`'s constructor until 2026-09-18, and that worked at run time while leaving the **XAML designer with nothing to resolve against**: Visual Studio builds its design-time `Application.Resources` out of `App.xaml`, so with none, forty `{StaticResource}` uses came back as `XDG-0001` on a window that compiled and ran perfectly — WPF resolves them at load time, not at compile time. `UI.Shared/Controls/BrandHeader.xaml` already did exactly this one level down, for the same reason, so the shape is the repository's own; and it is the more honest place, since which resources one particular window wants was never the application's business. **The two properties on the `Window` tag itself became property elements below `Window.Resources`**: an attribute is set as the parser reads that start tag, before it has reached a dictionary declared underneath it.
- **It opens small, in a corner, and grows when TIA answers** (2026-09-21, off a real station, and **confirmed on the VM**: with the full-sized window the confirmation dialog was covered and the attach could not go on; small, it is visible and the engineer can allow the access): TIA Portal asks the engineer to confirm that an application may access the project, and it asks *while this window is starting*. A window of 1180 by 860 centred at that moment sits on top of the box it asks in, and the two then wait for each other — TIA does not answer the attach until somebody confirms, and nobody can confirm a dialog they cannot see. **Small was not enough by itself**: TIA centres that dialog, so the waiting window is parked at the bottom right of the work area instead, where it reads as a notice beside the question rather than over it. It is centred again when it grows, since the corner was never a position anybody chose. **Growing is one way** — attached is the last word, so a second trip through the chooser cannot shrink the panels — and **every growth after the first keeps the centre it has**, so a window the operator moved stays where they put it. The chooser gets a size of its own, 720 by 520: the account of where the loader looked is longer than it is wide, and it is not going to show the panels.
- **x64, unlike every other satellite**, for the mirror image of the Add-In's reason: this process loads TIA's own 64-bit assemblies into itself rather than being loaded into TIA.
- **One window per project, since 2026-09-19** — see decision 6 for the rule; this is what building it taught. It was deferred here because the window could change nothing, and a guard is a decision about what the second launch should do; importing and moving settled that.
  - **`SingleInstance.PathKey` is the one way a path becomes a mutex name**, moved out of the config editor's private helper when this became its second consumer. The class that builds `Local\<Product>.<id>` is the one that imposes the constraint — a backslash separates the mutex namespace — so it is the one that should answer it. The config editor's keys did not move: the same hash of the same lower-cased path, checked against the old helper.
  - **A claim that loses now lets go of its handle, and that was a latent bug in every consumer.** The guard is the *existence* of a named mutex, and a name exists while any handle to it is open, so a refused claim that kept its handle kept the winner's mutex alive after the winner had gone. It never showed because every refused process exited at once; a window that gives way *after* attaching, in a process a test keeps alive, is what found it.
  - **Bringing the other window forward finds one of the same executable, and the first one**: with two projects open, the window brought forward can be the other project's. `SingleInstance` knows a name, not a window, so a fix would mean publishing the owner through something other than the mutex — not worth it until somebody meets it.
- **`ParentProcess` is duplicated from `Satellite.ConfigEditor`, deliberately and with the debt written down.** The one home both could share is `UI.Shared`, whose naming principle is that it holds what a *window* needs; `Core` cannot take it either, being loaded inside TIA with its references the intersection of its consumers' needs. **A third consumer settles it** — extract it then, beside `SingleInstance`, and accept that the name stops fitting.
- **The menu entry is on the PLC and on the project root, and was on the PLC alone until 2026-09-21** (the maintainer's decision both times). The reason for keeping it off the root was that a core belongs to one PLC's software, so an entry there would have to ask which PLC it meant — and the window had nowhere to ask, because it read the project the moment it opened. **Making the load manual is what removed that**: a window opened from the root comes up with the project's PLCs in a drop-down, counts what the first one holds, and waits, which *is* the asking. The action keeps the two apart — `ExecuteForProject` names no PLC where `Execute` refuses a device item that is not one — because "nobody pointed at a PLC" and "this is not a PLC" are different facts and want different sentences. **An entry on a block is still refused**: that would offer a whole-PLC operation from a single object. Which executable to launch comes from a literal in each `AddInController`, because **no Siemens API exposes the running TIA version** — the only thing that knows is the project the file is compiled in.
  - **The command line keeps its three positions**: the root sends an empty first argument, which the window already read as "nobody said" — the same rule the third argument follows for a project that was never saved. Nothing in the satellite changed for this.

### Mapping a project against its core — stage 3 built 2026-09-16

What the TIA project actually holds, written to `repo\project.json` — the other half of every comparison.

- **Everything is mapped, not only what looks like the core**, and the maintainer asked for it in those words: a block can have been downloaded into the wrong folder, or a folder built by hand can hold core blocks. From a list of core blocks alone only one of the three discrepancies is visible — *wrong version*; the other two, *here and it should not be* and *here but in the wrong place*, need the objects the core has never heard of as much as the ones it has.
- **A block says where it belongs, and that travels with it.** The TITLE's `family` is `core/adt/queue`, and held against the folder the block is actually in, a misplaced one is detectable **without the repository being reachable**. Cross-checked against the real core: `family` matches the node's own folder on all 264.
- **The TITLE reader agrees with the generator, measured on all 249 sources** — status, `deprecatedBy`, version and dependency count, file by file. That is the test worth having: two implementations of one contract in two languages, checked against each other rather than against what either was assumed to do.
- **Strict parsing, unlike `run.py`.** The generator scans the TITLE with a tolerant regex so a stray comma still yields its dependencies; being tolerant *differently* here would give two readings of one file, which is worse than one refusal naming the block. A title that is not JSON is not a problem at all — it is a block that is simply not from the core, which is most of a real project.
- **The arguments are `<PLC> <unit|*>`, and two arguments are not a handoff**: no document, no payload type, no pair of ends that can disagree about a selection. The Add-In's entry is on a PLC, where no unit is selected, so it sends the star — a starting point the window can change, not a decision. `*` itself is `Core.Places.GeneralProgram`, promoted out of `StyleReport` the moment it had a second consumer.
- **V21 gave `PlcBlock` and `PlcType` a `Title`; V20 has neither, and the untyped escape hatch does not help.** A real divergence, found by compiling one file against both, and the reason these two adapters are the first that are *not* line-for-line identical. `IEngineeringObject.GetAttribute("Title")` was worth one call and the VM answered it: *"'Title' is not supported by type 'Siemens.Engineering.SW.Blocks.OB'"*. Asked once and never again — it is a property of the TIA version, not of the object, and thousands of identical refusals would bury the map's own problems.
- **So V20 exports every block and every type to read its title**, which the maintainer chose over the alternatives when the gap was measured. A block would otherwise be identified only by its native `VERSION` and `FAMILY` headers — enough, since those are what a comparison runs on — but **a `PlcType` has no header at all in *either* version**, so with no title there is nothing left and a core UDT looks like one of the plant's. That is 91 of the core's 249 sources, which is not a footnote. `Core.Repo.PlcProject.SimaticMlTitle` reads the title back out, beside the interface reader that already does the same thing in the same TIA version.
- **It is not free and it says so.** One export per object, so a PLC of four hundred is four hundred of them; the window counts as it goes, because a window that says nothing for minutes is one an operator concludes has died — which this project has already paid for once. `ExportOptions.None`, since the file is read for one string and deleted a moment later. The file is a single reused `read.xml` under the project's own `repo\tmp\`, written, read and deleted per object, and the folder goes at the end of the run: what is in it is somebody's source code, and that is the same reason the coding-style check puts its scratch there rather than in `%TEMP%`.
- **A refusal is named for the first ten and counted after.** A PLC where every block is know-how protected would otherwise bury the map's other problems under four hundred identical lines.
- **The session now lives on one thread of its own**, which stage 2 deferred and this could not. Openness objects belong to the thread that obtained them; a walk of several thousand cannot be a snapshot and must not be on the UI thread. `TiaWorker` owns the thread and the queue, creates the session inside it — so a machine with no Openness still gets a window with a sentence — and hands every answer back on the UI thread, so no caller has to know which thread it is on.
- **A map with holes says where they are.** A folder that failed to read is a line in `problems`, not a silent omission: the one outcome a comparison must never be handed is a map that looks complete.
- **Written to a temporary file and moved into place**, so a run that fails half way leaves the previous map rather than a truncated one — and read back only when its `format` is one this version knows.
- **Indented, without `Newtonsoft.Json`.** `JsonReaderWriterFactory` makes the writer `DataContractJsonSerializer` uses underneath and that one takes an indent flag. The file is generated, but it is generated to be *looked at* when a comparison says something surprising.

### Choosing what to map — stage 3b built 2026-09-16

The maintainer asked for it once both satellites were attaching: *"para que no tarde tanto en el mapeo de los bloques podemos filtrar por OB, FC, FB, DB, UDT, TagTable, en OB, FC, FB filtrar por el tipo de lenguaje… así antes de mapear solo selecciono lo que quiero del proyecto"*. It is a performance feature with a correctness half, and the correctness half is the one worth writing down.

- **The filter is applied before the export, which is the whole of its value.** In V17–V20 the map is one export per object; the kind and the programming language are typed property reads that cost nothing. Filtering after the read would pay the minutes and then discard the answer — so `MapFilter.Wants(kind, language)` is asked at the leaf of the walk, above the line that exports.
- **The tick boxes are built from counts of the project itself**, so the choices come from what is there rather than from a list in the code: `ProgrammingLanguage` has twenty-nine values and a project uses four or five, and `SCL (312)` answers the question an operator actually has where a bare `SCL` does not. **The counting is `Core`'s**, through `ProjectSurvey.Building()`: the adapter knows how to reach an object, and how many of a kind there are is not a TIA question.
  - **This was a walk of its own — `ITiaSession.Survey` — until 2026-09-23, and it is gone**; see *One walk, at Load* below. What it counted, the map's own walk now counts as it goes, so a survey first and a map afterwards was two passes over one tree for an answer one of them produced anyway.
- **Empty means everything, and nothing ticked is refused rather than read as empty.** A filter nobody filled in is the absence of a decision and the safe reading of that is the whole scope; an operator who has just cleared a column has very much made one. The two readings would contradict each other in the one place it matters, so the *window* refuses — the button switches off and says so — and the contract underneath stays simple.
- **A language filter must not touch what has no language, and the first version of that rule was wrong.** `Wants` passed a null language and nothing else, so a caller handing it an empty string dropped every `PlcStruct` and every `PlcTagTable` — 91 of the core's 249 sources are data types. There is no language called `""` to tick, so null and empty can only mean the same thing; it now reads `IsNullOrEmpty`. **Found by a test, not by review**, and the test existed because the docstring had already named this as the thing that would be silently wrong.
- **A filtered map records its filter.** `ProjectMap.Filter` is written only when it narrows something, and the window's heading says *"Of what was ticked, not of the whole scope"*. Read back without it, a map covering only FBs says the project has no FCs, which is exactly the silent hole the map exists not to have.

#### A language belongs to its kind — the grid, 2026-09-17

The maintainer asked for it as a layout — *"Una columna con los objectos… a cada objeto ponemos en su fila los lenguajes accesibles"* — and the layout turned out to be the correct data model, which the first version was not.

- **Two flat lists cannot express the ordinary request.** `kinds` and `languages` side by side meant unticking `SCL` to drop a function block took every SCL *function* with it; "the SCL functions and every data block" could not be said at all. `MapFilter` is now one entry per kind, each naming the languages wanted inside it, and `ProjectSurvey` counts the same way — the survey could report 40 SCL objects and 31 FBs and never which of the two the SCL was in.
- **A kind entry with no languages is the whole kind**, which is the "empty means everything" rule one level down, and is also what a kind with no language at all looks like: a PLC data type and a tag table have none.
- **`project.json` went to format 2, and an older one is refused rather than half-read** (format 3 since 2026-09-23, which added `counts`). Its `filter` names members this version cannot see, so it would deserialize into a filter that narrows nothing and read back as a map of the whole PLC. **Both directions are refused now** — where a coding-style report deliberately reads an older workbook with its missing columns empty, because that is somebody's record of a moment. This is a snapshot of what the project holds right now and is rebuilt by one click, so refusing costs nothing and reading it wrong costs the thing the document exists for.
- **The rows read in the order a PLC does** — OB, FB, FC, the data blocks, then the types and tables — and not by count, which was the first version. Most-numerous-first moves a row whenever the project changes, and a row is looked for by name. A kind the order has never heard of follows by name, so one added to the object model appears rather than vanishing. The *languages* inside a row stay ordered by count: there the question is what that row is mostly made of.
- **The grid is built in code, not in the XAML.** How many rows there are and what is on each is a property of the project; the file carries the two headings and nothing else. The rows are removed by counting past those headings rather than by remembering how many there were, so a heading added later cannot be deleted by a number that quietly stopped matching.
- **A future GRAPH needs no change here, which was the point of asking.** Nothing lists what languages a kind *can* have — that would be Siemens vocabulary inside a binary, versioned by TIA release, which this project has refused three times. The day a GRAPH block is in the project it is counted under its kind and appears on that row.
- **A block whose language cannot be read is kept.** `Language` answers null on a refusal, and null passes — being dropped by a choice made about something else is the worse of the two failures.
- **Tick-box labels are a `TextBlock`, not `Content`**, and here that rule earns its keep rather than being observed on principle: `F_DB` and `Motion_DB` are real values of the enum, and WPF would render them `FDB` and `MotionDB`.

### Comparing a project with its core — stage 4 built 2026-09-17

`core.json` on one side, `repo\project.json` on the other, and **metadata only** — the maintainer settled that in those words. Comparing sources would mean deciding what a formatting difference means; the question this answers, *is this the block the core stands behind*, is answered by what the block says about itself.

- **The plumbing existed and nothing called it.** `LocalSource`, `LocalCopy`, `PlcCoreCatalogLoader` and `PlcCoreValidator` were built and tested in stage 1 against the real core, and a grep over the satellite found not one reference — it did not even read `config.json`. `Core.Repo.PlcCoreRefresh` is the line that joins them, and it is one call rather than five steps a window has to get in the right order: the copy has to happen before the catalogue is read *out of* the copy, and a caller that got that backwards would compare against whatever the last run left behind.
- **A project that names no core is a normal state**, and the window says so rather than reporting a fault. `coreSource: null` is why that value exists at all. `remote` said "not wired up yet" until the GitHub core landed; it now comes down the wire like any other, and what the window says instead is why it could not — no token, no such repository, the rate limit, no network — each in its own sentence.
- **Findings are a list per object, not a verdict.** A block can be outdated *and* in a folder its family does not otherwise use, and collapsing that into one word loses half of what has to be fixed. Six of them: `Outdated`, `UnknownVersion`, `Misplaced`, `Disagrees`, `NotFromCore`, and `Absent` for the other direction.
- **The TITLE decides and TIA's header is the fallback, and a disagreement is its own finding** (the maintainer's choice). The TITLE is the contract the core's generator writes; the header is all a V17–V20 block has when the export fails, and a PLC data type has no header at all in either version. A block whose two versions differ is neither up to date nor outdated — it says two things, and what it needs is an edit rather than an import.
- **`1.1` and `1.1.0` are one version.** `System.Version` keeps a component nobody wrote as `-1`, so the two compare unequal — and they arrive from a hand-typed TITLE and from a `System.Version` rendered back to a string. Without normalising, every block whose header carries a build number disagreed with itself. Found by a test.
- **Nothing compares one version as greater than another** (the maintainer's choice, and the tolerant one). Outdated means `core.json` marks *that* version deprecated; a version the graph does not list is `UnknownVersion`, with the versions it does list beside it so something can offer them. The day two majors are live again, both are right answers and neither is reported as behind.
- **`UnknownVersion` with no versions beside it is the whole answer to a block that claims a `core/` family it is not entitled to.** `core.json` is the source of truth, so a name the graph does not carry is not part of the core — said once, rather than as a second finding meaning the same thing.
- **A family is compared within one tree, and the first rule was wrong.** The core's `family` is a path in the *repository*, `core/node`, while a project folder is whatever the hierarchy calls it, `Program blocks/03-ALL`; there is no mapping between the two and inventing one would put somebody's folder names inside a binary. What needs no mapping is that a family belongs together — but `core/node` holds an FB *and* the UDT it works on, and TIA files those under `Program blocks\…` and `PLC data types\…`, **two folders by construction**. The first version reported every such family as split. The grouping now carries the folder's first segment, which is TIA's own word for the tree and is only ever compared with itself. **No majority is taken**: with two blocks in two folders there is no majority, and naming one the odd one out would be a claim this layer has nothing to base on.
- **`Absent` is silent on a filtered map, and says so.** A map of the FBs alone cannot tell "the project has no UDTs" from "this map did not look for them", and answering the first would report 91 data types as missing from a project holding every one. It is the same reason `project.json` records its filter at all.
- **Only what the core still stands behind can be absent.** Listing a retired version as missing would offer to import something the core has itself withdrawn.
- **Nothing is written to disk.** `project.json` is the durable half — a snapshot that took minutes to read — and the comparison is recomputed from it and the project's copy of `core.json` in the time it takes to open a window. A second file would be a third thing to keep in step.
- **The comparison does not run on the worker's thread.** `TiaWorker` owns the one thread Openness objects belong to, and none of this touches TIA: it reads a configuration, copies one file and parses two. Putting it there would queue a file copy behind a walk for no reason but habit.
- **Every count is named on screen, zeroes included.** "0 outdated" is the answer somebody pressed the button for; a line missing from a list says nothing at all.

### The two panels — stage 5 built 2026-09-17

*"Projecto a la izquierda, Repository a la derecha"*, which the maintainer settled at the start and this builds.

- **Both sides are trees, and both are open** (the maintainer's correction, the same day). The left began as a `ListView` with five columns; making the two panels the same shape is what lets them be read against each other, and a panel folded away is one you have to go looking through. The columns lost nothing: the folder became the path, and the kind, version and message became the line.
- **The project tree comes out of the map, not out of a rule here.** A mapped object's folder already begins with TIA's own name for its tree — `Program blocks/03-ALL/adt`, `PLC data types/node` — because the walk starts at the software's root groups, so the window only adds the one root the map covers: the unit, or `*`. Nothing invents `Program blocks`, which would be a translated Siemens name inside a binary.
- **Every line says something.** A core block with nothing against it reads *up to date*, rather than being the one line on either side that trails off — the repository side always has a state to give.
- **The kind is spelled as the map spells it** — `GlobalDB`, `InstanceDB`, `PlcStruct` — which is `CodingStyleNames`' vocabulary and the one the filter rows at the top of the same window already use. The maintainer offered `DB`/`UDT`; it reads faster and hides the difference between a global and an instance data block, which the map does draw, and it would give one window two vocabularies for one thing.
- **The counts became the filters**, which is the shape the coding-style report already settled on, and the tick boxes are the same control this window uses twice above rather than a new kind of chip. **"Not from the core" starts off**: in a real project it is most of the rows and this window is about the core — but the box stays on screen with its count, so nothing is hidden without saying how much.
- **Any ticked finding is enough to show a row.** A block that is outdated *and* in the wrong folder belongs under either, and requiring both would lose it from the one filter somebody opened.
- **A folder the tick boxes empty is not drawn.** Folders exist in either tree only because something is in them, so filtering to the outdated shows the folders holding outdated blocks rather than the whole tree with two leaves in it. **An empty folder therefore cannot appear at all** — the map records objects with paths, not folders — which is a limit of the map worth stating before it is read as "there is no such folder".
- **The repository panel holds the whole core, not the gap** (the maintainer's choice). What a window offers to import is not only what is missing: a block held at a retired version, or one sitting where its family does not otherwise live, is downloaded again too, and a list of the absent alone could offer neither. Only *current* nodes, though — offering a retired version would be offering to import something the core has itself withdrawn.
- **As a tree of the core's own folders** (the maintainer's choice), which is how the repository is laid out and what makes stage 6's tick boxes worth having: marking a folder marks what is in it.
- **The repository has its own tick boxes, by state** — `In the project`, `At another version`, `Absent` — which is how "show me what is missing" gets asked with both trees open, and the first thing importing will want. **`Not covered` appears only when a filtered map produced any**: on every other run it would be a box that never does anything.
- **The folder comes from the node's own `file`, not from a family in a TITLE.** `core.json` is the source of truth and it carries the path; the family is what a *block* says about itself, and the two agreeing on all 264 nodes is a fact about today's core rather than something to depend on.
- **`Absent` is muted and `Held` is marked.** Absent is 241 of 247 rows in a project that has taken a handful of blocks, and colouring the majority says nothing; what is worth picking out is what the project already has, and where it has something else.
- **A filtered map makes a node `Unknown`, not absent** — a fourth state rather than a lie. What the map *did* cover is still answered: if a block is in there it is in the project, whatever else was skipped.
- **The words live in `ComparedRow`, not in the window**, for the reason `ReportLine` records one satellite over: a finding is named in the table *and* on the tick box that filters it, and two spellings of "outdated" is how a filter stops matching the rows it names.
- **One results area, two things in it.** A walk and a comparison are never both true at once, and stacking them would leave a map's counts under a comparison of a different scope — so every path that writes a sentence puts the panels away first.

### Downloading and importing — stage 6 built 2026-09-17

The maintainer set the flow out: *"eliges el bloque > click en download > descarga el bloque seleccionado y sus dependencias como fuentes > importa las fuentes > las fuentes se guardan en el proyecto en la carpeta que marca su familia"*. **The first thing in this framework that changes somebody's project**, which is what every decision below is shaped by.

- **The API was read off the assembly before any of it was designed**, and it decided the shape: `ExternalSources.CreateFromFile(name, path)` then `source.GenerateBlocksFromSource(group, option)`, whose **two overloads take a `PlcBlockUserGroup` or a `PlcTypeUserGroup`** — so the destination folder is an argument rather than something to move things into afterwards. `PlcBlockUserGroupComposition.Create(name)` makes the folders. **Both adapters compiled against the real V20 and V21 assemblies**, which is what turns those from claims into facts.
- **Two things reflection could not answer, and they were written down rather than assumed. The VM has since answered both.** `GenerateBlockOption` is only `None` or `KeepOnError`, so there is no `Override` on the source route, and what TIA does when the block already exists was a VM question until 2026-09-19: **it overwrites it, silently, and where it is** — no refusal, no message, and the new block left in the old block's folder, the group handed to `GenerateBlocksFromSource` ignored. The first half is what `DownloadAction.Replace` had assumed; the second broke the promise that a download puts a block where its family says, and is what the next section fixes. The other was `PlcTagTableComposition.Import` taking a bare `FileInfo` with no format, on the maintainer's word that TIA imports a tag table from `.xlsx`: it does, from its own user interface, and **Openness does not expose that door**.
- **The plan is made first, and it is pure.** What the operator is shown and what the import then does come from one answer rather than from two walks that could disagree. `DownloadPlan` is exercised against the real 264-node core with no TIA anywhere near it.
- **Dependencies come from the graph's edges, and only where the edge resolved and is not external.** 147 of the core's 296 edges are external — `TP_TIME`, `TON_TIME` and the rest of Siemens' own — and none of them is ours to import. The first test picked a node whose only dependencies were exactly those, which is how that filter got confirmed rather than assumed.
- **Dependencies are planned before what needs them.** A UDT has to exist before the block whose interface names it, so the order is the plan's answer rather than something the importer works out again. Depth-first, with the node recorded before descending so a graph that points back at it stops rather than going round.
- **Ticked is replaced; a dependency already at the core's version is left alone — by default.** Asking for a block you already have is asking for it to be put back, which is how a misplaced or hand-edited one gets repaired. A dependency that is already right is the cheapest correct answer the first time — and the wrong one the second, see the next section.
- **Who else depends on an entry is worked out for every collision** — **excluding blocks already in the plan**, since those are about to be written too — and shown beside it before anything is written. That was the maintainer's refinement when only a dependency at another version was asked about, and it is the safety of the whole feature: replacing a dependency changes the behaviour of every block that calls it, including blocks nobody selected.
- **The impact check says what it cannot see.** The project's dependency lists come from each block's TITLE, so a block of the plant declares nothing and cannot be counted. An empty answer means "no *core* block depends on it", never "nothing does", and the window says so — an all-clear that is really a floor is worse than no check.
- **Nothing is compiled and nothing is rolled back.** TIA refuses an inconsistent block and compiling would change the project behind an operator who asked for an import; Openness has no transaction, so a refusal half way leaves what already went in, named in the report. Deleting blocks somebody asked for because a later one refused would be the worse outcome.
- **The external source is deleted again.** It is a step, not something the project should keep: one per imported block would fill a folder nobody asked to fill, and the next download would meet its own leftovers. `KeepOnError`, because a source that generates three blocks and fails on the fourth has still produced three the project wants.
- **TIA reads every source out of `repo\tmp\`**, never out of the repository: `CreateFromFile` reads from where it is pointed, and a file in somebody's working tree is not the project's to hold open. The download brings the sources there itself, just before the import — see *A Load copies the graph, and a download its own sources*. Until 2026-09-22 they were copied into `tmp\` from the mirror under `repo\core\`, for the same reason one level down.
- **The comparison on screen is thrown away after an import, and the window reloads by itself** (2026-09-18). Throwing it away is right — it described the project as it was a moment ago — but the first version stopped at two empty trees and a sentence saying *map the project again*, which is the same defect the walk itself had one step earlier: what was just written is the whole reason for looking. An import and a move now both end in what *Load* does, and that is the one thing this window still starts on its own — it is not deciding to read a project, it is showing what a write just did to the one it was already showing.
  - **What the write had to say outlives that reload**, which is the one thing it cannot replace. The summary and every refusal go into a notice that sits above whatever else is under the panels, because the reload rewrites both captions and the status line — leaving the line an operator most needs to read as the first thing to disappear. It is cleared when the next write starts, or by a *Load* somebody asked for themselves.
- **The tick box is on the node, not on the folder.** A folder tick would be a second thing to keep in step with what is under it after every filter change, and the dependency closure is what saves the clicking anyway.

### What a download meets, and where it leaves it — 2026-09-19

Two things the VM found and one the maintainer asked for, in one message: *"el objeto no se mueve a la carpeta de su familia"*, *"si descargo un objeto con dependencias por segunda vez, solo se instala el objeto, las dependencias no se descargan"*, and the order a core folder is read in.

- **An object the project has elsewhere is taken out and generated again where its family says** — **confirmed in TIA on the VM (2026-09-21)**, for a block and for a tag table — because TIA overwrites where it stands and Openness has no move. Exported, deleted, generated into the family's folder — the same forced order *sync folders with core* already uses, for the same reason: a name is unique across a PLC's software. `Relocated` in each adapter is the one place it happens, and **it decides by what TIA holds, not by the map**: the block is looked for in its family's folder first, and only when it is not there is the rest of the tree searched. The map's folder is what the window *shows*; it can be a walk out of date.
  - **One that will not export is not deleted**, and is replaced where it stands with the reason in the report. **The one branch of this the VM could not try**: it takes a know-how protected or inconsistent object, and the core has none. A know-how protected or inconsistent block is refused on the way out, and a copy that cannot be made is a delete with no way back. The report calls it written, not failed: it is the core's object now, and *sync folders with core* is what moves it once it can be exported.
  - **One whose replacement will not generate is put back where it was.** A failed download must not cost the project a block it already had — which the silent overwrite never could, and deleting first could. A source that produces nothing of that name counts as not generating, checked by name in the family's folder rather than trusted from a clean return.
  - **Only when even that fails is it stranded**, and then exactly as a move is: the file kept and named in the report — in `repo\stranded\`, where it was written before the object was deleted. It was in `repo\tmp\` until 2026-09-22, kept by the adapter declining to clear that folder, and cleared by the next run that did not — see *An object that is only a file*.
  - **A tag table is found anywhere too**, where it used to be looked for in the family's folder only — so a table of that name elsewhere made the create fail, the name being unique. It is exported before it is deleted and put back if the new one cannot be made, the one rule this feature keeps everywhere.
- **Whatever a download would meet, it asks first** (the maintainer's design): a window listing every entry — ticked blocks and every dependency — with a tick box, what the project already has of it and where, what ticking it would do, and who else uses it. **Nothing the project has is written without being on that list**, because TIA will not refuse the overwrite and nothing else would stop it. A download that meets nothing goes straight in: a window confirming a list of imports is one the operator learns to click through, which is the habit the other case cannot afford.
  - **It replaced the message box that asked only about dependencies other blocks used.** That one could say what would change behind somebody's back, and could not be told to do more — which is the second request: the plan leaves a dependency alone when the project already has it at the core's version, so downloading a block again brought the block and none of what it needs. The plan's proposal is now only where the ticks start; `All` is the second download.
  - **`DownloadPlan.Taking` is what comes back**: the same plan, entries in the same order, ticked ones imported or replaced whatever the plan first proposed and the rest kept as skips — kept rather than dropped, so the report still says they were left as they were. The window is `Satellite.CoreUpdater.Download`, its rows carry their own words for the reason `ComparedRow` does, and it is pure over the plan: nothing is written by asking.
  - **Leaving out a dependency the project does not have is allowed and marked red**, not prevented. It is the operator's call — they may be about to write it by hand — and a window that refuses a tick is one that has decided it knows better than the person in front of it; the line says what will happen.
  - **No `BrandHeader`, and a status bar.** It is a question the core updater asks rather than a window of its own, so a second header would repeat the one behind it; the bar stays, because here it has something to say — what the ticks add up to, and the button is off while nothing is ticked.
- **A core folder reads blocks, then data types, then enumerations** — `.scl`, `.udt`, `.xlsx`, by name inside each (the maintainer's order). By name alone `_queue` came out between two enumerations, and a folder read as a list of names rather than as a function and what it works on. The sort is `PlcCoreComparison`'s, so every reader of `Repository` gets the same order; the extension is the core's own answer, as it is for the import.

### A core that lives in GitHub — `remote`, stages 1 and 2 built 2026-09-21

The last piece of the configuration contract that was never implemented: `coreSource: remote`, with `coreRemoteRepositoryConfig` naming an owner, a repository, a branch and a folder. The maintainer chose the order — *"primero implementaremos core de Github y luego el release"* — and the two decisions that shape it.

- **The download is a tree and one blob per file, not a zipball** (the maintainer's choice, offered against the one-request alternative). A zipball is one call and brings the whole repository every time it moves; the core is one folder of a repository that holds several families and its tools. Two calls give the listing, and after that **only what changed comes down**.
- **The client is a project of its own**, `src/GitHubApi\`, with no reference to `Core` — the same shape as `S7PlcWebserverApi` and for the same two reasons: it can be exercised from PowerShell against a real repository without the framework, and **it must never reach `Core`, which is loaded inside TIA Portal's process and may not take `System.Net.Http`**. `Core` declares the port `IRemotePlcCore` / `IRemoteFiles`; `Satellite.CoreUpdater.Remote.GitHubPlcCore` is the joint, and it is thin because everything worth testing is on one side or the other of it.
- **What comes down lands where the local copy's does** — the graph at `repo\core.json`, the sources a download needs in `repo\tmp\` — per project, not versioned, and read back exactly as a local core is. `LocalSource` was written for this a week early — *"whatever fetches from GitHub ends by producing a folder on disk, and from that point the two are the same thing"* — so the catalogue, the comparison, a download's sources and *sync* never learn where the core came from. **No shared cache under `%LOCALAPPDATA%`**: it stops being one answer the moment two projects follow different branches, and a comparison has to be able to point at the core it was against. (This said `repo\core\`, the whole folder, until 2026-09-22.)
- **The copy is its own index, and that is what makes the second run free.** GitHub's sha for a file is git's hash of its content, and the same hash can be computed from the file already on disk — so nothing has to be written down about what was fetched last time. An index file would be a second thing to keep in step, wrong the moment somebody edits the copy; `GitBlobSha` makes a hand-edited, truncated or deleted file repair itself, because its hash no longer matches. **It is not a plain SHA-1 of the bytes**: git hashes `blob <length>\0` and then the content, and getting that wrong fails silently — every file downloads every time and nothing looks broken.
- **A source the branch no longer lists is refused by name**, never fetched from an older commit. While the whole folder was mirrored the rule was that whatever the repository did not list was *removed* from the copy, so a retired block could not be compared against; with nothing mirrored there is nothing to remove, and the same fact now stops a download instead.
- **Bytes are held against the hash that was asked for before they are written**, and a file is written beside its destination and moved over it. A proxy, a truncated response or a dropped connection cannot leave half an `.scl` under a name an import will read.
- **A graph that did not come down whole is refused, not compared against**, and the previous copy is not compared in its place: a Load that says "compared" is saying the core is the one the repository holds now.
- **`repo\core.origin.json` records which commit the graph was read at, and is deliberately not a shortcut.** Skipping the listing when the branch has not moved would save one request and give up the self-repair, so it is not taken; what the marker is for is saying *which core a result was against*, which nothing could say before — a local core is named by a folder that has moved on, a remote one by a branch that has, and a commit stays true. It is only written when the graph came down whole.
- **The token never enters `config.json`.** The file carries `${REPO_TOKEN}`, `PlcCoreRefresh` resolves it through `Core.Secrets` from the per-user `.env`, and **an unresolved reference is no token rather than an empty one** — which is exactly how a public repository is read, and for a private one the refusal that follows names the variable to set.
- **A 404 with no token is reported as a token problem**, because that is what GitHub answers for a private repository read by nobody; believing the status would send somebody to check a name that is correct. **But a missing branch on a readable repository asks one more question** — does the repository exist? — so it can say which of the two it was. And a refusal from an `apiUrl` that is not the public API names that URL, since a wrong one in `config.json` otherwise reads as a token problem too.
- **A truncated tree is refused rather than filtered.** GitHub stops listing at around a hundred thousand entries and says so in one field; a core read from a partial listing is one missing blocks with nothing saying so.
- **Redirects are not followed, and that is a bug found by a typo** (2026-09-22, while running the whole chain against the real private repository for the first time). Asking for `PLC-Framework/code` — the owner's old name — came back as *"GitHub's rate limit has been reached. API rate limit exceeded for 185.222.166.83"*, which is the **anonymous** limit, on a call that carried a perfectly good token. The cause is measured: GitHub answers **301** for a renamed repository or owner, and **`HttpClient` on .NET Framework drops the `Authorization` header when it follows one**, so the followed request arrives anonymous. `/rate_limit` with the same token answered 5,000 an hour at that moment. Left alone, that sends an operator to check a token that is fine or a name that is merely old.
  - **Following it with the header re-attached would work and is still wrong.** A core's identity is the one written in `config.json`; a silent follow leaves that file stale for good while `core.origin.json` records a repository the configuration does not name. So `AllowAutoRedirect = false` and a move is **reported by name** — `GitHubMovedException`, its own type because it is its own instruction: not a token to check, one line to edit.
  - **GitHub does not put the new name in `Location`** — it answers `…/repositories/1301869263`, the numeric id — so the destination costs one more request, made **only on the way to failing**, the same bargain `Missing` already strikes for a 404. **And the redirect keeps the rest of the path**: asking for a branch is sent to `…/repositories/<id>/branches/main`, and a branch has no `full_name`, which is why the first version of this answered *has moved* and could not say where. It asks the repository, two segments up. A second request that goes wrong costs the destination, never the message.
  - **Switching the redirect off had to be held against the blobs**, since a large one could well be sent to a CDN: the whole 275-file core came down again through the new handler, unchanged.
- **`Core\Repo\` is split by where a core comes from** (2026-09-21, the maintainer asked for it once both halves existed): `Local\`, `Remote\` and `GitHub\`, with the namespaces to match — `Core.Repo.Local`, `Core.Repo.Remote`, `Core.Repo.GitHub` — and everything that is about a core *once it is a folder* left at the root, because the catalogue, the comparison, the map and the plans do not care which half brought it.
  - **The local half was renamed so the pair reads as a pair**: `RepoSource` → `LocalSource` (and `Local(config)` → `Of(config)`, which stopped reading as `LocalSource.Local`), `RepoCopy` → `LocalCopy`, `RepoCopyResult` → `LocalCopyResult`. `Repo*` was a fine name while there was one kind of repository and a misleading one the day there were two.
  - **They are the same contract with two transports, and the difference is what each can afford.** Both answer the same two calls — `Graph` for a Load, `Sources` for a download — and write to the same places. A remote copy asks before it fetches, because a file costs a request; a local one has the file under its hand, where comparing costs the same read as copying, so it copies what it is asked for every time and needs no hash. The results differ for the same reason: `LocalCopyResult` counts files copied, `RemoteCopyResult` counts downloaded against kept and carries the commit. Merging them would mean one type with two halves that are null by turns.
  - **`GitBlobSha` sits under `Git\`, and it was under `GitHub\` for a day** (corrected 2026-09-22, looking ahead to GitLab). Nothing in it is one host's: git hashes `blob <length>\0` plus the content, and GitHub, GitLab, Gitea and Azure DevOps all answer that same blob id in their listings — so a second provider needs no second hash, and a folder named after one of them said the opposite. `Core` now has no folder named after a vendor at all. **`RemoteCopy` still names that folder in a `using` with the reason beside it**: the copy is only incremental because the listing answers a content hash it can recompute from disk, so a remote that was not a *git* host would answer something else and that file is where it would be learned — as `IRemoteFiles.Matches`, since only the provider knows what its identifier means. Not built, because GitLab costs nothing here.
- **The two things being compared then got a folder each — `PlcCore\` and `PlcProject\`** (2026-09-21, the maintainer's words: *"para no confundir el Core de la solución con el PLC core del repositorio del usuario"*). `Core` is the name of this solution's bottom layer **and** the name of the maintainer's block library, and the second meaning had been living inside the first: `Core.Repo.CoreCatalog` is a catalogue of the *PLC* core, and nothing in the name said so. `PlcCore\` now holds `core.json` and what a core object carries — the catalogue, its loader, its validator, `PlcCoreRefresh`, `BlockMetadata` and `ConstantsWorkbook` — and **the types were renamed to match**: `CoreCatalog` → `PlcCoreCatalog`, and likewise the loader, the validator, `PlcCoreRefresh`, `PlcCoreLoadResult`, `PlcCoreRefreshResult`, `PlcCoreStatus`, `PlcCoreConstant`, `PlcCoreTag`. `BlockMetadata` and `ConstantsWorkbook` kept their names: neither ever said "Core", so neither was ambiguous. **Four more followed on 2026-09-22**, the last that still said `Core` for the PLC core: `CoreComparison` → `PlcCoreComparison` and `CoreNodeState` → `PlcCoreNodeState` (the maintainer's), `CoreOrigin` → `PlcCoreOrigin` and `IRemoteCore` → `IRemotePlcCore`. `repo\core.origin.json` kept its name — it is a file on disk in projects that already have one, and the serializer writes no type name into it, so a marker written before the rename still reads.
  - **`PlcProject\` is the other half of every comparison**: `ProjectMap`, `ProjectMapFile`, `ProjectSurvey`, `MapFilter` and `SimaticMlTitle` — `repo\project.json` and everything that makes it. **Those names were left alone** because they already say *project*, and `ProjectMap` was never going to be read as this solution's `Project`. `SimaticMlTitle` went with them although it never touches `project.json`: reading a block's title out of an export is what V17–V20 must do to build the map, and that is the only thing it is for.
  - **What stayed at `Repo\`'s root is what belongs to neither side**: `PlcCoreComparison` is the *join* — it names both halves and cannot live in either — with `DownloadPlan`, `SyncPlan` and `ImportReport` downstream of it, and `RepoPaths`, which is the layout of `repo\` as a whole. A file at the root is a file about both cores or about the folder; a file in a subfolder is about one of them.
- **A second host is a `provider` key, not a wider `coreSource`** (2026-09-22, the maintainer put it in the template first and asked for `Core` to follow). `coreSource` answers *a folder on this machine or a repository over a wire*; `provider` answers *whose API*, and widening the first to `github | gitlab` would have broken every `config.json` already saying `remote` while mixing the two questions in one word. **Absent is `github`**, because that is what every file written before the key existed says by omission — the reading is "the only provider there was", not "nobody decided" — and an empty string is a value outside the set, reported like any other, for the reason `coreSource` already records.
  - **The closed set is `Core`'s and it holds one name today.** `RepositoryValidator.ProviderOf` normalises (trimmed, absent → `github`, never silently corrected) and `Knows` answers **Ordinal**, so `GitHub` is refused exactly as `Local` is on `coreSource` and the message says what to write. A configuration naming another provider is refused three times over — validator, JSON Schema, and `PlcCoreRefresh` before a client ever sees it, which since 2026-09-22 is the same validator called from there rather than a copy of its rule.
  - **That third refusal is the one that matters**, and it is why `PlcCoreRefresh` validates rather than leaving it to the port: a client for one host handed another host's configuration would read `owner` and `repository` off it and talk to the wrong place, which is the single failure that would come back looking like an empty core rather than like an error.
  - **Nothing in the framework knows the token's variable name** — `Token()` expands whatever `${...}` the file holds — so a GitLab project writes `${GITLAB_TOKEN}` and no code changes. The only places `GITHUB` is spelled are the template, the schema's example and `Satellite.ConfigEditor`'s field.
  - **`PlcCoreRefresh.FromGitHub` became `FromRemote`, and its three sentences stopped saying GitHub**: the dispatch was always on `remote`, so a GitLab project would have been told about GitHub in a window. They name the provider the file asked for instead.
  - **`repo\core.origin.json` gained `provider` and `apiUrl`**, and its line reads `acme/code@main on api.github.com, commit abc1234`. Owner, repository and branch are not an answer on their own: the same three on GitHub and on GitLab are two different cores, and a marker that could not tell them apart was the half-truth it exists to close. A marker written before those keys still reads, and simply says nothing about the host rather than guessing one.
  - **What is deliberately not built**: a `RemoteCores` dispatcher picking an implementation per provider. It belongs in the satellite, where `MainWindow` already passes the one `IRemotePlcCore` there is, and it is a factory of one line the day there are two — the seam is in the right place, which is the whole point of writing this down now.
- **Stage 3, the window, built 2026-09-22 — and it is one line under the core tree.** What the framework knew and the screen did not say was *which core this was compared against*: `PlcCoreOrigin` was written and never read, and `PlcCoreRefreshResult.Fetched` and `.Copied` had no reader at all, so a local core and a remote one at a named commit gave the identical caption. It now reads `Repository — PLC-Framework/code@main on api.github.com, commit abc1234 — 247 current nodes, …`, or the repository folder for a local one.
  - **The answer comes from the run, not from the marker read back.** `PlcCoreRefreshResult.Source` is set by both halves — the core folder for a local refresh, `PlcCoreOrigin.ToString()` for a remote one, built **once** and used twice so the file on disk and the line on screen cannot drift. A result must never describe a core other than the one it just read, which a marker from a previous run could. `PlcCoreOrigin.Read` therefore still has no caller, and that is right: it is a record for whoever opens `repo\` later, which is what its own header claims, not a shortcut the window needs.
  - **Both halves answer it, and the local one needed it most.** A remote core is named by a commit that stays true; a local one is named by a folder that moves on with nothing recording which state it was in — so the folder is the most that can honestly be said, and saying it beats saying nothing.
  - **What it cost is said only when it was not nothing.** A second remote refresh downloads no file, because the copy is its own index, and announcing it every time would bury the one run where it is worth reading — so the caption says *"core.json updated"* only when the graph came down. A local copy is one file every time and says nothing at all. (Until the mirror went this counted files, *"17 downloaded, 232 already here"*, and a local one what it had **removed**.)
  - **The progress while it comes down was already wired and is now checked rather than assumed**: `Load` hands `PlcCoreRefresh` a delegate that writes to the status line, and `RemoteCopy` calls it — *"Asking the repository what it is at…"*, *"Reading the repository's file list…"*, *"Downloading core.json…"* on a Load, and *"Downloading 1 of 2 - queueInstanceAttributes-v3.0.udt"* on a download.
  - **Exercised with a stand-in port rather than over the wire.** What talking to GitHub does is already measured against the real repository; what is new is that the refresh hands the origin back, and a fake serving one file says that without spending 249 requests of an hourly sixty. Trying it the other way is what proved the point: the first run of this test hit the rate limit on file 60.

### A Load copies the graph, and a download its own sources — 2026-09-22

The maintainer asked why a remote Load brought every source down when the comparison reads one file, and settled the design in three messages: *"importar siempre el último commit, es fuente de verdad"*, *"cada load … solo copias las fuentes que serán importadas, es muy ineficiente copiar todo el repo local o remoto porque no en todos los proyectos del PLC se usan todas las librerías del core"*, and *"repo/core debe desaparecer, cuando copias de local o remote, solo copias la fuente, la carpeta destino en TIA Portal ya se describe en core.json"*.

- **What the mirror cost was not a detail.** A first remote Load was 277 requests — the branch, the listing and 275 files — against GitHub's **sixty an hour without a token**, so a public core could not be loaded at all by anybody who had not made one. A local one copied the whole library into every project on every Load. The comparison is metadata only and read one file of it.
- **A Load now copies `core.json` and nothing else**, to `repo\core.json`, and reads the catalogue from there. Measured against the real private repository: **one file in 2 s, where it was 275**, and a second Load downloads nothing, the graph's own hash being its index.
- **`repo\core\` is gone, and a Load takes away one it finds** — `PlcCoreRefresh.Retire`, best effort and silent, read-only files included since a checkout can leave them that way. It is generated and not versioned; a folder that will not go today is tried again on the next Load, and failing to delete it is never a reason to refuse a comparison.
- **A download brings its own sources, at the moment it needs them.** `PlcCoreRefresh.Sources` runs after the download window has been answered and before the worker imports, for exactly the entries that will be written — a skip brings nothing — into `repo\tmp\`, where the import reads them and which it clears at the end unless something was stranded there. The same folder a move exports into and V17–V20 read titles through, so the project has **one** scratch folder rather than a second one per feature.
- **From the branch's head, always**, the maintainer's rule: the repository is the source of truth, and an import brings what the core holds now. **A source the head no longer lists is refused by name** rather than fetched from the commit the Load read — that would import a core the repository has stopped standing behind. **When the head has moved since the Load, the import still goes ahead and says so**: *"The core moved since it was loaded - compared at abc1234, imported from def5678."* The plan was made from the older graph, so the operator is told; refusing would contradict the rule it follows from.
- **All or nothing.** A source that did not come down stops the whole import, with the reason: an import missing one is one whose dependency may never arrive, and the object that needed it would then fail to build as the *import's* fault.
- **Flat, because TIA's destination was never the file's folder.** A source lands in `tmp\` under its own file name; where it goes in the project comes from the node in `core.json`, as it always did. **Two sources sharing a file name are refused, both of them** — measured on today's core, 268 nodes carry 268 distinct names, case-insensitively too, so the refusal is for the day that stops being true rather than something anybody meets now.
- **`RepoPaths.CoreFolder` had been doing two jobs, and removing the mirror is what showed it.** It named the mirror under `repo\` *and* the hierarchy's own `core` folder in TIA, where `DownloadPlan` puts every core object — two unrelated folders that happened to share a word. Deleting the constant with the mirror would have left the second without a name; keeping it would have left one constant meaning both. `DownloadPlan.CoreFolderInTia` is its own now.
- **Nothing in the copy layer deletes any more**, so the guards a mirror needed went with it: a destination overlapping its source could have had the clean-up delete the repository itself, and a copy that only ever writes named files has nothing left to guard. `LocalCopyResult` and `RemoteCopyResult` lost `Removed`; `PlcCoreOrigin` stopped counting files, and a marker written before still reads.
- **A download with nothing left to fetch asks the repository nothing** — two requests out of an hourly budget, spent on habit otherwise.
- **Verified**, which is what makes this more than a refactor: the copy layer against the real 268-node core and against a repository held in memory — a graph alone under `repo\`, sources flat and only those named, a second run fetching nothing, a hand-edited file repaired, bytes that are not what was asked for never written, a source the head does not list and a name two sources share each refused by name; the whole chain against the **real private repository** with the maintainer's token — the retired folder removed, `repo\` holding `core.json` and `core.origin.json` and nothing else, a download of `_queue` bringing exactly its two sources with each equal to **git's own blob id at the head**, and nothing written containing the token; the paths built **under the tightest partial trust**; and every window test on top. **And confirmed in TIA Portal on the VM (2026-09-22)**, which is the one thing no double here reaches: TIA imports from a source that arrived in `tmp\` this way, the scratch folder is cleared when the run ends, and `repo\core\` is not created at all.

### An object that is only a file — `repo\stranded\`, 2026-09-22

Openness has no move, so moving an object is an export, a delete and an import, and between the delete and the import the export is the only copy. A download taking an object out of the wrong folder does the same. The design always kept that file and named it; **what it did not do was keep it long**.

- **It lived in `repo\tmp\`**, and a run that stranded something declined to clear the folder. But the next import or move that ended well cleared it whole, and so did **every V17–V20 Load**, whose map reads each title through `repo\tmp\read.xml`. The only copy of a block lasted exactly until somebody did the next ordinary thing.
- **The export is now written in `repo\stranded\` from the start**, rather than written somewhere else and rescued on failure: when the object goes back in, the file is deleted; when it does not, it is already where no clean-up reaches. `Core.Repo.StrandedFiles` names the path — `move-_queue.xml`, `replace-_queue.xml` — and `repo\tmp\` is cleared at the end of every run without conditions, since nothing in it is ever the only copy of anything.
- **A name already taken is never handed out.** A file with that name may be an object an earlier run stranded, and exporting over it would destroy the one copy there is; `move-_queue (2).xml` is taken instead.
- **The path is asked for before the export**, and nowhere to put it throws a sentence — so a folder that cannot be made refuses the move while the object is still where it was.
- **The window says so from the moment it opens, and on every run after**, as a paragraph of its own above anything else under the panels: how many exports, where, each by name, and what to do. The report that named a stranded object the first time is gone the moment the window reloads, and a file that survives is only worth anything if somebody is told it is there.
  - **It is asked for where the line is written, not by the callers, and the VM is what settled that** (2026-09-22). The first version composed it in the two paths that end a comparison, so a window opened on a project with a stranded object said **nothing** until somebody pressed Load — and a refusal afterwards wiped it, because the other five callers write that line without it. It is read in `Problems` now, which every path goes through. **Said before anything is read**, too: what is in `repo\stranded\` is a fact about the project's own folder rather than about TIA, and this window deliberately reads nothing until Load.
- **Verified here**: the paths — made safe, never over an existing file, the folder made on the way, a refusal with no project folder — the listing oldest first, and the real window after a Load, with the warning present and gone once the folder is empty.
- **On the VM (2026-09-22) it ends empty, which is the whole of what a good run should leave**: every export written there went back into the project and was deleted again, `repo\tmp\` was cleared, and `repo\core\` was never created. **The refusal branch stays unexercised, and for the reason already on record**: it takes an object TIA will not import back, which means a know-how protected or inconsistent one, and the core has none. So the folder has been shown to be built, used and emptied; that it *keeps* a file is still reasoned rather than measured.

### `Core` put in order — 2026-09-22

Asked for as a review — *"Está Core optimizado y ordenado correctamente?"* — and answered point by point, the maintainer choosing each.

- **The `core.json` model moved under `Repo\PlcCore\Graph\`**, namespace `Core.Repo.PlcCore.Graph`. It had sat at `Core`'s root as `Core.DependencyGraph`, outside the split the maintainer chose for the PLC core, and the namespace carried a type of the same name — the namespace-and-type trap this file already warns about, which is why two files needed `using CoreGraph = …`. The four types kept their names, because they mirror the generator's own models and were checked against them field by field; the JSON does not change, the serializer writing no namespace into it.
- **One file per type** — the rule under *Rules not to break*; twenty-six types moved out of fourteen files, each in its own folder and namespace as before.
- **Four members nothing read were removed or renamed.** `CodingStyleChecker.BrokenRules` went: every row offered a broken rule already says so, because the rule is missing from the compiled set. `PlcCoreRefreshResult.Copied` went: a local copy is one file, whose failure is the refresh's refusal and whose success `Source` already names. `LocalCopyResult.IsComplete` became `Ready`, the word its remote twin uses. `CoreOrigin`, `IRemoteCore` and `GitHubCore` became `PlcCoreOrigin`, `IRemotePlcCore` and `GitHubPlcCore`, the last types still saying "Core" for the PLC core.
- **One helper writes every file in `repo\`** — `Core.SafeFile`, at `Core`'s root because the `.env` may want it too. The graph, the map, the sources and `core.origin.json` each had their own "write beside, delete, move", and between the delete and the move there was no file at all; it swaps with `File.Replace` and falls back to the old order only where the volume refuses. `core.origin.json` was written in place.
- **Checked with the compiler, not by eye**: the whole solution builds with no warning, `Core` has no unneeded `using` by IDE0005, and every test here passes — the copy layer against the real core and a repository held in memory, the refresh against the real private repository, the paths under the tightest partial trust, and the windows on top.

### One walk, at Load — 2026-09-23

The maintainer, on opening v1.1.0: *"me he fijado que con Core Updater cuando carga la app hace un 'load' silencioso, creo que el load debe hacerse solo con clic"* — and then the design, when the two halves were laid out: *"si para hacer filtro hay que recorrer una vez y luego con el load se recorre otra vez el project, es una tontería, hacemos el recorrido del proyecto con load y ese unico recorrido vamos sacando la info del filtro"*.

- **The window read the project every time somebody looked at it, and that is what he saw.** Stage 3b's survey is a walk — the same tree, counting instead of reading — and it ran when the window opened *and* on every change of PLC or software unit. Opening the window on a project, or glancing at another unit, spent a pass over the tree on a question nobody had asked; and the Load that followed walked it a second time. **Nothing measured it wrong: it is cheap in V21 and one pass in V17–V20 too, the export being what costs.** What made it wrong is that it was spent unasked, which is the same argument that took the automatic Load out two days earlier and stopped one step short.
- **The count is now the map's own, taken before the filter is asked.** `Mapped` reads the kind and the language, hands them to `ProjectSurvey.Found`, and only then asks `MapFilter.Wants` — so the numbers cost nothing whatever the filter keeps, and what pays is the line underneath, which is one export per object in V17–V20. `ITiaSession.Survey`, the two `Survey` implementations and the three `Counted` overloads are gone, and with one job at the leaves the three delegates the walk switched on went too: `Walk` calls `Mapped` directly.
- **They count what was *visited*, not what was kept**, and that is what makes the boxes usable twice. A filter that recorded only what it let through could afterwards be narrowed and never widened — each run forgetting what it had left out — so a map of the FBs alone would come back offering FBs and nothing else. Counting at the top of the leaf is one line and closes that for good.
- **And they travel in `repo\project.json`**, as `counts`, which is what lets the window offer a filter without reading anything: opening on a project mapped before is a parse of one file. Format 3, and an older map is refused in both directions exactly as before — its `filter` names members this version cannot see. `ProjectSurvey`, `SurveyedKind` and `Counted` became `[DataContract]` with public setters for it, the same shape `MapFilter` already had beside them.
- **A scope never mapped simply has no boxes, and the first Load pays for the whole of it** (the maintainer's choice, in one line: *"pagamos el peso del load completo"*). No boxes is no filter, which is what "empty means everything" already says at every level of this feature — so nothing had to be invented for the case. The alternative was a *Count* button, which is the unasked pass over the tree under another name, and it was not built.
- **The boxes are read back only for the scope they describe.** `repo\project.json` holds one map, so a map of another PLC — or of the whole program where a unit is now chosen — answers nothing rather than putting somebody else's numbers on screen. A map this version cannot read answers nothing through the same door, `ProjectMapFile` refusing it.
- **A Load rebuilds them only when there were none**, which is the first load of a scope. The walk counted the whole scope whatever the filter kept, so rebuilding would be right about the numbers and would throw away the ticks the operator had just loaded with — and the next press of Load would quietly be a full one again.
- **The caption says where the boxes came from** — *"The tick boxes are what the last load of this scope found"* — and says it only when there are any. A window claiming a last load it has not got is the half-truth this one has spent every stage refusing.
- **Verified here**: the counts through the round trip, languages inside their own kind and a kind with no language keeping none; an older `project.json` refused with the message naming *Load* rather than the *Map project* button that no longer exists; and on the real window — boxes on screen with nothing read and the caption saying so, then a PLC never mapped taking them away, hiding the panel, and leaving Load on.
- **And confirmed in TIA Portal (2026-09-24)**: opening a project reads nothing, the tick boxes come back from the last map, and one press of *Load* walks, refreshes and compares. **Faster too — the maintainer's word, with no number taken**, which is what removing the pass predicted rather than a second measurement of it: a window opened on a project now costs nothing at all, where it used to cost a walk of the whole scope before anybody had asked for one.

### The log — `Core.Logging`, 2026-09-24

The gap `add-in-for-tia-portal`'s `Util\Logger` left behind, and the maintainer's requirements in one line: *"Log completo de lectura/escritura, excepciones"*. Then the design, which changed twice for the better while it was being built.

- **Per user and per application: `%LOCALAPPDATA%\PLC-Framework\logs\<app>.log`, with the project as a column on the line** (the maintainer's design, reached in two steps). It was first `.plc-framework\logs\` inside each project, then one file per project in the per-user folder, and both hit the same wall: **a run learns its project only after it has started writing**. The core updater gets it from an attach that can fail or be settled by the operator, so a file named after the project either waits in memory or moves house halfway through a run — and the part of a bad run before there is a project is exactly what somebody sending a log needs. One file per application removes the question; the project is a filter, which is the same reason the coding-style report made PLC, unit and object columns rather than one path. It also means nothing a run writes lands in a versioned folder, and "send me the logs" is one folder.
- **`ConfigPaths.Logs` went with it.** It had been the one project folder nothing wrote, flagged in this file as "exactly when two components drift apart on a string", and now nothing ever will.
- **Measured before it was chosen, twice.** Under the tightest partial trust, time with its offset, `TimeZoneInfo.Local` and `Guid` are allowed; the user name, the machine name, `Process.GetCurrentProcess()` and every file operation are not. With what `Config.xml` declares, all of it works **except the PID** — so a run is named by a short `Guid`. And `Environment.GetFolderPath` demands `FileIOPermission`, the permission writing into the project already needed, so the Add-In reaches the per-user folder at no extra cost. `%LOCALAPPDATA%` does not redirect it, which is why the tests write under `probe-*` names of their own and remove exactly those.
- **A file shared by two processes is taken exclusively for each write, and that was the finding worth the whole of phase 0.** `FileMode.Append` on .NET Framework seeks to the end at open and writes from its own position, so two writers overwrite each other **silently** — no exception, no torn line, whole lines missing from a file that looks perfect: 2,000 of 4,000 survived a shared handle, 2,617 opening per line, 4,000 opening exclusively with a 250 ms retry, at about 0.1 ms a line. **The first run of that measurement said 600 of 600 for the shared handle and was wrong**: starting a process takes longer than writing 300 lines, so the two never overlapped. Both writers are released from one gate now.
- **One write is one block**, so an exception's stack goes under its message without another process landing inside it — a consequence of the exclusive open rather than a design of its own. Every other message is flattened to one line, blank lines dropped.
- **Nothing throws and nothing is required to work.** No folder, no permission, no application name: a log that writes nothing and says so. A line that cannot be written after the retry is counted, and the closing line reports it.
- **Secrets are masked by shape** — GitHub and GitLab tokens, `Bearer`, a value after `password=` or `token=` — **and `${REPO_TOKEN}` is left as it is**, since it is the framework's way of saying where the secret is not. `token` followed by a space is deliberately not a trigger: the first version turned "the token expired" into "token ***".
- **4 MB, then one `.1`.** Six applications share six files, so the megabyte that suited one file per project would have held too little of each.
- **The core updater is the first consumer** (stage 2.1). The log is opened by the application before anything else, so the assembly resolver's account of where it looked — on screen only until then, and gone with the window — is in the file; then what the Add-In asked for, the attach, each Load, the map's holes, the core compared against, every import and move, and every failure with its stack. **A walk's successful exports are not logged one by one**; the refusals are, as the map's own problems, with the summary (the maintainer's choice: the export itself is TIA's to record, and a line per object is 40 KB a Load in V17–V20 saying "it worked" four hundred times). **V20 and V21 share `core-updater.log`**, told apart by the version on their `started for` line (the maintainer's choice too): they are one application built twice because Openness forces it, where the two Add-Ins are two packages TIA loads apart.
- **Verified here** with the real executable, which on a machine without TIA writes the resolver's refusal and nothing else, and by 31 + 10 checks and a race of two processes on two projects losing no line. **Confirmed on the VM (2026-09-24)**: the file is created and filled by a real attach.
- **The other three satellites log too** (stage 2.2, 2026-09-25), each opening its log in `App` before reading the handoff and closing it in `OnExit`, and each recording what escapes every handler — `DispatcherUnhandledException`, with the stack, and **not handled**: recording a crash is not a reason to pretend it did not happen.
  - **The config editor** records the handoff, a window giving way to another over the same file, the file opened — missing, not parsing, or with its problem count — the template a new one started from or why it could not, and every save: refused with the first problem, written, or failed. **`REPO_TOKEN written to the .env` names the variable and never the value.**
  - **The coding-style report records what arrived on the thread that read it**, before the window shows it, so a window that fails to show a report does not also lose the record of it. **An input closed with nothing in it is two different facts**: on the waiting path the Add-In promised a report, so it is a warning that the check did not finish; read at startup it is a window started by hand. The first version called both "started with no report", which is the half-truth the window itself had already been built to refuse. Import and export are recorded with their path and what the report held — scope, rows, failures, format.

### A tag table is built object by object — 2026-09-17

**The VM refused the workbook**, which settles the one thing stage 6 wrote down as unverifiable. `PlcTagTableComposition.Import` reads whatever it is handed as SimaticML: *"EPriorityQueueMethod: Error when calling method 'Import' of type 'Siemens.Engineering.SW.Tags.PlcTagTableComposition'. Invalid XML encountered while reading Simatic ML file: Data at the root level is invalid. Line 1, position 1."* TIA Portal does import Excel — from its own user interface. Openness has no such call, and the premise that it did was the maintainer's and mine both.

- **So the table, its constants and its tags are created one at a time**, which the assemblies do offer: `PlcTagTableComposition.Create(name)`, `PlcUserConstantComposition.Create(name, dataTypeName, value)` and `PlcTagComposition.Create(name, dataTypeName, logicalAddress)`. All three compiled against the real V20 *and* V21 assemblies, which is what turns them from a reflection listing into a fact.
- **`Core.Repo.PlcCore.ConstantsWorkbook` reads the workbook, and not with `DocumentFormat.OpenXml`.** Writing a real `.xlsx` is five XML parts in a zip whose only true test is whether Excel opens it, which is why the SDK earned its place for the exports; *reading* a shape this file already knows is one zip entry and two documents. And `Core` may not take that package at all — it is loaded inside TIA Portal's process — so it takes `System.IO.Compression` instead, a framework assembly that process already holds. What makes the reader worth anything is not the parser but the **fifteen real workbooks** it is run against.
- **Sheets by name and columns by header, never by position**, and both were measured rather than assumed because both would have been wrong. `EAdtConstants` puts `Constants` first and `system` puts `PLC Tags` first; the parts are not reliably `sheet1.xml` either, one file in the folder calling its first part `sheet.xml`. The three sheets are `Constants`, `PLC Tags` and `TagTable Properties`.
- **The first row of `Constants` names the table and carries its `TITLE` — and is a constant like every other, which the first version got wrong.** Its `Name` is the table's, its `Value` a placeholder, and its `Comment` is the same JSON a block carries, read by the same `BlockMetadata`. Checked against `core.json` on all fifteen: the name equals the node's `base`, and version, status and family agree with the graph. It was read for those two things and then **skipped**, so an imported table came out without the one constant that says where it came from. **There is nowhere else that could live**: `PlcTagTable` has a `Name` and nothing more — no `Title`, no `Comment`, in either TIA version — which is why `TiaSession` reads a tag table's metadata out of *the comment of the constant named after it*, and why the workbook puts it there. The symptom was two screens away from the cause: the table imported fine, the next map could not tell it from one of the plant's, the project tree hid it under "Not from the core" (which starts off), and the core tree matched it by name with no version at all — *the project has v*.
- **The `Path` column is `core\adt\EAdtConstants`** — the family with the table's own name appended — so a table is placed by its family like every other object in a download. **The `TagTable Properties` sheet is deliberately not used for that**, although it has a `Path` of its own: it reads `90_LIbrary\ADT\ADT`, which is where the table sits in one plant's tree rather than where the core says it belongs, and a table placed by it would land somewhere *sync folders with core* then wants to move it out of.

### Putting a misplaced object back — *Sync folders with core*, 2026-09-17

The maintainer asked for it in the same message as the layout: *"mueve los bloques en project que sean del core y que no estén en su respectiva carpeta"*, and chose the mechanism: *"es más fácil si exportas e importas en .xml, te basas en el core para destinar en la carpeta"*.

- **Openness has no move, and that was checked rather than assumed.** All 2,269 types were searched for one — no `Move`, no `Cut`, no `Reparent`, no `ChangeGroup`, no `Relocate`. So a move is an export, a delete and an import, and **the order is forced rather than chosen**: an object's name is unique across a PLC's software, so the copy cannot go into its new folder while the original is still in the old one.
- **Which leaves a window in which the object is only a file, and the whole report is shaped around it.** A move whose import fails keeps its export and names the path in the refusal — and the export is written in `repo\stranded\` from the start, which no run clears. An object nobody can find again is the one outcome this must never produce. (Until 2026-09-22 it was in `repo\tmp\`, and a stranded file lasted until the next run that ended well; see *An object that is only a file*.)
- **The plan is the comparison's `Misplaced` rows and nothing else.** The panel above the button already shows them and already says what is wrong with each; working the list out a second way would be two answers to one question, and the first time they disagreed the button would move something the tree called correct.
- **An object is found by name, never by the path the map recorded.** A name is unique across a PLC's software, so a walk by name is exact — where a path begins with a tree name that follows TIA's interface language, and taking that apart here would put a Siemens word inside a binary. **Which tree to start from comes from the kind**, which is `CodingStyleNames`' vocabulary and the same in every language; everything that is not a `PlcStruct` or a `PlcTagTable` is a `PlcBlock`.
- **`SyncPlan` names a family, never a TIA folder.** `core/adt/queue` is the core's own word for where a block belongs; which tree that sits under is TIA's, and the adapter is what puts the two together.
- **`ExportOptions.WithDefaults`**, unlike the coding-style check's throwaway export: this is the whole object on its way back in.
- **A tag table moves this way too, and here SimaticML is the door that works** — what comes *out* of a project is SimaticML, so a move needs none of the object-by-object building a download does. The PLC's default table is refused by name: TIA rebuilds it, and it never comes from the core.
- **It asks first, and it is the second prompt in this window.** Every object is named against its destination, up to twenty; past that a list stops being read. The prompt also says what a move *is*, because "for a moment this object is only a file" is worth knowing before it happens rather than after.
- **Only a comparison enables it.** There is nothing to find before the project has been compared, and the button's state is set where the comparison lands rather than kept in step by hand.

### `config.json` pipeline — contract settled 2026-09-08, validators built 2026-09-09

**The field-by-field contract lives in `docs/configuration.md`, under *The `config.json` contract*** — required, type and meaning for every key, plus the closed sets, the internal references and the uniqueness rules. It is the authority; do not restate it here and do not infer requiredness from the model, which is permissive on purpose. (It was in the README until the documentation was split; this line said so for longer than it was true.)

The shape of it, worth carrying in your head:

- **`metadata.coreSource` decides the file.** `local` or `remote` selects which of the two repository sections is required; the other one is not validated at all. **`null` — or no key — means no repository** (2026-09-13): a core is needed only by the actions that read one, so requiring it made every project invent a path.
- **Lists are required but may be empty.** `[]` says "no folders for this concern"; a missing key says nothing. Applies to all four `hierarchy` lists and all six of `codingStyle`.
- **Two internal references** are what a typo breaks silently, so both are checked: `implements` must name an existing `rules[].id`, and `rules[].id` is unique file-wide.
- **`Group.name` is unique among siblings only** — the same name in another branch is fine, because they are different folders.
- **A `regex` that does not compile is a structural error**, not an environmental one: it is a broken file, not a broken machine.
- **No Siemens vocabulary in the code: every name is checked and the configuration decides** (2026-09-15). TIA writes names into a block's interface that nobody can rename — an OB's `Initial_Call`, a GRAPH block's `INIT_SQ` and `RT_DATA` — and the obvious answer, skipping them, was proposed twice and rejected by the maintainer both times. Two signals looked usable and neither is: `Informative="true"` on a `<Member>` marks only *some* of them, and the `Informative` on a member's `<Comment>` also marks the GRAPH steps and transitions, whose names the engineer types and whose rules the reference configuration already carries (`sequence_variable`, `transition_variable`). Either would have put Siemens' vocabulary, versioned by GRAPH release, inside a binary. The template carries two interface rules instead — `interruption_parameter` for an OB's `Initial_Call` and `Remanence`, `graph_parameter` for a GRAPH block's six — assigned to the sections where TIA writes; **a rule is edited by whoever meets the problem, a binary is not**. Both **name the parameters outright and anchor at both ends**: a pattern by shape was tried first and it swallowed the engineer's own names, passing a step called `S001_Init` that `sequence_variable` would have failed. The structural exception stays: a member typed by a UDT, a library FB or GRAPH's own `GRAPH_BASE` is not descended into, because those names belong to that type and are checked there — that is about where a name is declared, not about who chose it.

`config.json` has **two producers** (`Satellite.ConfigEditor`, and the user editing by hand) and **one consumer** (the Add-In). Decisions taken:

- **DTOs stay permissive**, validation is a separate pass. A serializer that throws stops at the first problem and loses the rest; a validator reports all of them with their location.
- **Validation lives in `Core` and runs twice**: in the satellite before saving, in the Add-In after loading. Validating only in the UI is useless — hand-editing bypasses it.
  - **And the Add-In half was missing for the hierarchy until 2026-09-22.** `CheckCodingStyleAction` validated its own concern from the start; `CreateProjectHierarchyAction` took whatever the file said and walked straight into TIA, which is how `HierarchyValidator.Validate` came to be a public entry point with no caller — the smell that found it. **Nothing was ever corrupted by that**, which is why it lasted: `Ensure` steps over a blank name and `FindOrCreate` answers the folder a duplicate names. What it cost was **silence** — a nameless folder, or two siblings spelled the same, came back *"Hierarchy ready"* with a count one too high, and the defect the editor paints in red was never mentioned again. **It refuses the whole walk now rather than running as far as the first bad name**: a folder tree half created is one nobody can tell from a tree somebody built by hand. The validator is called with the `projectConfig.hierarchy` prefix, so each issue points into the file as written, and the message stops naming problems at ten and counts the rest — the same shape the coding-style check already had.
  - **The repository concern's had the same hole, found the same day** — `RepositoryValidator.ValidateRemote` and `ValidateLocal` had no caller. `PlcCoreRefresh` checked `coreSource` by hand, `LocalSource` checked the local fields by hand, and an empty remote field reached the client, which answered *"An owner is required. Parameter name: owner"* — a sentence naming no field of `config.json`. **`RepositoryValidator.Validate(config)` is the one entry point now**: `coreSource` and the section it selects, and not the rest of `metadata`, so a mistyped `version` does not stop a comparison. `PlcCoreRefresh` calls it before touching the disk or the wire and refuses in **one line** naming each path — one line because it lands in a caption under the core tree, where the hierarchy's refusal is a message box. `ConfigValidator` shares the same section selection rather than repeating it. **It also closed a contradiction**: `PlcCoreRefresh` read `coreSource: ""` as "no core", where the contract says an empty string is a value outside the set; only `null` means no core now.
- **Scoped per concern, not per document.** Each action reads only its section, so no section is globally required; "required" belongs to the concern. The satellite runs the composite validator, an action runs only its own.
- **Structural vs environmental** validation kept apart: closed value sets, required fields, internal references and regex-that-compile are pure; checking a path exists or a `${VAR}` resolves touches disk and belongs in a separate method.
- `coreSource` is `local | remote | null`, and it decides which repository section is required — none, for `null`.
- The `.env` lookup is environment-specific (Add-In vs satellite resolve it differently) → it becomes a `Core` port, with `${VAR}` expansion pure in `Core`.
- A **JSON Schema** is the highest-leverage addition for the hand-edit path: it validates while the user types, before any of the above runs.

The single-version machine also confirmed that a TIA that is not installed is *reported and stepped over* rather than failing the run. **The installer does not create the `.env`.** It runs elevated, so `%LOCALAPPDATA%` could be the administrator's profile rather than the engineer's — the same trap as `%AppData%` in step 2 — and the config editor already creates it in the right place on first use
- [ ] Try the TIA Add-in Tester and/or `Siemens.Engineering.AddIn.DebugStarter.exe` to shorten the test cycle. **Planned for the next Add-In** rather than retrofitted onto the existing ones: the point is a shorter loop while writing something, and the two that exist are already validated on the VM.
  - **It is a VM tool, and that was measured rather than assumed** (2026-09-23). `TiaAddInTester.exe` takes `--path` (the `.addin`), `--provider`, `--menu` and `--item`, so it invokes one menu entry of a packaged Add-In. Run here against the real V20 package it answers *"No or more than one TIA Portal instance found, make sure only one TIA Portal is open!"* — it resolves the Siemens assemblies **out of a running TIA Portal**, and wants exactly one. The `Version=16.0.0.0` in the message is only what the 2022 tester was compiled against; the resolver is what answers it. **So it cannot run on the development PC at all** — TIA is not installed here and will not be — and what it buys on the VM is not "no TIA" but no clicking through the project tree, and a plain .NET process to attach a debugger to instead of TIA itself. **The open question that decides its worth**: what selection a simulated menu hands the item, since our actions read `GetSelection<DeviceItem>` or a list of blocks and would otherwise only exercise the project-level entries
